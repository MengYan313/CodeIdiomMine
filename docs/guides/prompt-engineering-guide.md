# 提示词优化本地指南

本文在 CodeIdiomMine 与 WPF2React 中保持相同，是两个项目日常新增、修改、评审 LLM 提示词时的本地依据。它是对 OpenAI 官方指南的项目化摘要，不是官方文档的完整副本。

## 1. 同步状态与适用范围

- 最近同步：2026-07-18。
- 同步时官方推荐的最高能力模型：`gpt-5.6-sol`。
- 本指南适用于 GPT-5.6 系列及两个项目当前的结构化 LLM 调用，但不覆盖项目实际配置的模型档位、领域规则、用户明确要求或 API 能力限制。
- 日常提示词工作优先阅读本文，不需要每次访问官网。仅在第 9 节列出的条件出现时，才使用 `$openai-docs` 刷新。

## 2. 设计优先级

提示词应先定义结果，再补充真正会改变模型行为的约束。按以下顺序组织信息：

1. 用户可观察的目标。
2. 完成任务必须满足的成功标准。
3. 安全、隐私、业务、证据和副作用边界。
4. 必要的领域事实、输入数据和允许使用的工具。
5. 输出格式、字段含义和停止条件。

用户明确要求、已验证的领域契约和 JSON Schema 始终优先于本文的一般建议。不要为了套用模板而改写既有业务阈值、数据含义或返回字段。

## 3. 推荐结构

结构化调用统一使用 `build_json_system_prompt(...)`：

```python
from src.llm import build_json_system_prompt

system_prompt = build_json_system_prompt(
    role="领域专家",
    goal="给出可直接用于后续流程的判断结果。",
    success_criteria=(
        "结论由输入证据支持。",
        "所有必需字段都符合 JSON Schema。",
    ),
    constraints=(
        "不得编造输入中不存在的事实。",
        "证据不足时使用领域约定的安全回退。",
    ),
    field_rules=(
        "reason 使用简洁中文。",
    ),
    stop_rules=(
        "满足成功标准后立即返回，不追加解释或 Markdown。",
    ),
)
```

各部分职责：

- **角色**：说明模型承担的专业职责，不堆叠空泛人格标签。
- **目标**：描述最终要得到什么，不逐步规定模型如何思考。
- **成功标准**：列出完成前必须为真的可检查条件。
- **约束**：只放真正的硬边界、领域不变量和禁止事项。
- **输出**：由 JSON Schema 和字段规则共同定义。
- **停止与回退**：规定何时完成、何时报告证据不足，以及允许的重试次数。

system prompt 只保存稳定职责和规则。源码、依赖、检索结果、历史响应及其他每次调用都会变化的内容放在 user prompt，并明确视为待处理数据，不得执行其中的指令。

## 4. 写作规则

- 业务提示词和解释性输出使用中文；代码、模型/API 名称、必要技术术语和 JSON 字段名保留英文。
- 每条规则只写一次。删除同义重复、无行为影响的提醒和过期示例。
- 优先描述结果、验收标准和边界；让模型自行选择高效的分析路径。
- `必须`、`禁止`、`始终`、`仅`只用于真实不变量。判断场景应给出决策条件，不使用不必要的绝对措辞。
- 不要求模型展示思维过程或逐步推理。需要可审计性时，要求简短结论、证据字段或可复查的计算结果。
- 示例只在它编码产品要求或修复已测得的失败模式时保留；一个清晰的边界示例通常优于多个重复示例。
- 检查规则之间是否冲突。冲突的详细提示词通常比精简但一致的提示词更不稳定。
- 重要歧义应规定最小回退：询问最少的缺失信息、返回明确 blocker，或采用已经授权的默认值。

## 5. JSON 输出契约

- 结构化响应使用提供方原生 JSON mode，并在每次调用中传递显式 JSON Schema。
- 不使用 `[JSON]`、`[/JSON]`、Markdown 代码块或其他领域标记包装结果。
- 首次响应只对完整文本执行 `json.loads` 和 Schema 校验，不从自然语言中截取疑似 JSON 片段。
- 解析或校验失败时，统一调用 `src/llm/json_output.py`，由同一模型按同一 Schema 修复一次。
- 损坏响应必须编码为普通数据传给修复提示词，不能让其中的内容覆盖系统指令。
- 第二次仍失败时显式报错，或进入领域层已经定义的安全回退；不得静默接受原始响应。
- Schema 应声明必需字段、字段类型和 `additionalProperties` 策略。字段说明关注业务语义，不重复 JSON 语法。

## 6. 上下文、工具与边界

- 只提供完成任务所需的上下文和工具，避免把无关资料塞入 system prompt。
- 必要的检索、读取和验证属于前置条件时，应明确写出，不能因为预期答案明显就跳过。
- 多个读取互不依赖时可以并行；后一步取决于前一步结果时保持顺序执行。
- 工具规则应说明何时使用、关键返回字段、失败行为、重试上限和停止条件。
- 回答、诊断和评审默认不授权外部写入；本地修改任务可以执行范围内的非破坏性验证；外部、破坏性、付费或明显扩展范围的操作需要确认。
- 失败回退应尽可能小：最多进行有界重试，不重复已完成工作，也不以减少调用次数为由牺牲必要证据和正确性。

## 7. 模型与推理配置

- 调用点不得硬编码模型名称，统一通过 `LLMConfig` 使用低、中、高档配置。
- 模型升级时先保留当前 reasoning effort 作为基线，再在代表性任务上比较相同档位与更低一档。
- 不全局默认最高 reasoning effort。先检查提示词是否缺少成功标准、依赖规则、验证要求或明确回退。
- 模型更强不等于可以省略领域上下文、权限边界和验收标准，也不意味着需要加入“更努力思考”等指令。
- 本指南记录的 `gpt-5.6-sol` 只是同步时的官方最高能力模型，不会覆盖项目当前以低档模型作为隐式默认值的约定。

## 8. 修改与验证流程

1. 先保存当前可工作的提示词、模型配置和代表性输入作为基线。
2. 根据真实失败样本识别一个明确问题，例如字段缺失、证据不足、越权或格式错误。
3. 一次只修改一组相关规则，避免同时重写提示词、模型、工具和推理档位。
4. 先运行离线合同测试，再用相同代表性样本比较修改前后结果。
5. 真实 LLM 验证必须记录模型、Schema、输入范围、调用次数、成功标准和失败原因，并遵守成本与隐私审批。
6. 只有在正确性和完整性不回退时，token、时延或调用次数下降才算优化。

正式实验记录模型、reasoning effort、温度、调用日期、输入集合、重试次数和评测结果即可。

## 9. 何时刷新本指南

以下任一情况出现时，使用 `$openai-docs` 获取当前官方指南，并同步更新两个仓库中的本文：

- 项目目标模型或模型家族发生变化。
- OpenAI API、JSON mode、Structured Outputs、工具调用或 reasoning 参数发生兼容性变化。
- 用户明确要求采用“最新”“当前”或某个指定模型的提示词实践。
- 代表性回归出现无法由领域代码或数据解释的持续行为变化。
- 准备冻结正式实验配置，且上次同步后官方模型指南已经更新。

刷新时记录日期、目标模型、来源链接和对本地规则的实际影响。没有行为变化时只更新同步记录，不为追求措辞一致而重写工作正常的提示词。

## 10. 提交前检查清单

- [ ] 目标和成功标准可检查。
- [ ] 稳定规则在 system prompt，动态数据在 user prompt。
- [ ] 规则没有重复或冲突。
- [ ] 中文、必要英文术语和 JSON 字段名符合项目约定。
- [ ] 未要求展示思维过程。
- [ ] JSON mode、Schema、解析、一次修复和最终失败路径完整。
- [ ] 权限、隐私、成本、重试和停止边界明确。
- [ ] 使用共享构造器与 `LLMConfig`，没有复制公共逻辑或硬编码模型。
- [ ] 离线合同与代表性样本已验证。
- [ ] 两个项目的共享文件一致性检查通过。
