# Parser 失败类型、兼容性与未解决风险

## 失败类型

| 类型 | 当前检测或缓解 | 剩余风险 |
|---|---|---|
| 条件编译破坏语法边界 | 原始异常统计；等长预处理影子；只在异常减少且函数数不下降时启用 | 不知道实际构建选择的分支；两个分支可能同时进入影子树 |
| 函数式/声明式宏 | 记录宏相关异常和未覆盖范围 | 不展开宏，宏生成的函数或类型仍可能不可见 |
| 不完整源码 | Tree-sitter 容错树；`recovered_function`；单文件失败隔离 | 恢复边界可能过宽；默认 quality-v2 会排除不干净候选 |
| 模板、Concept、Lambda | 穿过模板和类外壳寻找真实函数；区域包含 Lambda | 依赖类型推导的语义关系不可得 |
| 复杂声明 | 使用 Tree-sitter 范围和子树规模，不依赖正则切函数 | grammar 无法识别的编译器扩展仍形成 `ERROR` |
| `.h` 语言歧义 | 文件级覆盖、异常和路径可审计 | 扫描器只支持 C++，Objective-C/Objective-C++ 头会被当作 C++ |
| 编码异常 | UTF-8 优先、Latin-1 保底，并按原始字节映射 | 文本解码展示可能与项目实际编译编码不同；字节范围仍可信 |
| 文件读取失败 | 记录失败类型与消息，继续全局任务 | 主 pickle 不包含该文件的函数；必须查看侧车 |

## 语义切片风险

当前 Def-Use 是局部近似：

- 只在函数内分析，不解析跨函数调用关系；
- 按标识符名称连接最近的先前定义，没有类型、作用域消歧、指针别名、引用逃逸或成员敏感分析；
- 不建立完整 CFG，不区分互斥分支和不可达路径；
- 不计算控制依赖，控制语句主要通过连续跨度和核心操作进入片段；
- 连续源码要求可能带入依赖闭包之间的桥接语句；
- 语句单元来自容器直接子节点，深层嵌套关系由区域级二次分析而不是全局扁平化处理。

这些限制可能造成误切分或漏切分。缓解措施是要求实际 Def-Use 边、限制跳数和跨度、内聚度至少 0.5、排除错误容器、限制每函数最多六条，并在 `dependency_summary` 中保存可复核证据。正式研究实验仍应人工抽样估计有效性和冗余度。

下一步有通用价值的增强顺序建议为：

1. 为函数内基本块建立轻量 CFG，加入分支和循环控制依赖；
2. 使用作用域栈区分同名局部变量，并对字段访问做有限成员敏感处理；
3. 在不需要完整编译的情况下加入函数内 reaching-definitions；
4. 对可用 `compile_commands.json` 的项目提供可选 Clang 后端，而不是替换当前容错路径；
5. 在冻结语料上人工标注片段内聚性、冗余和边界准确性，再调整阈值。

## 映射与身份限制

- `source_file_id` 是相对路径哈希。仓库内移动文件会产生新身份；`source_sha256` 可用于判断内容是否相同。
- 为控制体积，文件身份只存于函数根和实际下游候选，不在每个 AST 子节点重复。直接消费裸子节点的工具必须从所在函数根继承身份。
- `extent` 使用 Tree-sitter 的行列点，`start_byte/end_byte` 是规范范围。包含非 ASCII 文本时，列是字节列而不是 Unicode 字符列。
- 影子树节点的范围可信，但结构来自遮蔽预处理指令后的文本；`parse_origin` 不能被忽略。
- v2 保留原始注释和空行，因此基于旧清洗文本哈希的缓存不会命中。应使用 `source_sha256`、字节范围和 profile 组成新缓存键。

## 下游兼容性

主 DataFrame 和阶段信息合同没有改变：

- `dataset.pkl` 仍为四列；
- `pros_info` 仍为 `[project, file, function_extent, node_info]`；
- 候选仍只有函数、区域和语句三个 `candidate_level`；
- `ast_num` 继续表示直接子节点数；完整子树使用 `subtree_size`。

新增 `fragments.pkl` 作为 Parser 到 embedding 的版本化中间合同。它保留既有
`pros_info` 内部结构，增加目标 tokenizer、预算、拒绝清单和逐项目统计，不改变
最终 `embeddings.pkl` Schema。行为变化通过 `fragment_schema_version=1`、
`mapping_version=2`、`candidate_origin` 和显式 profile 管理：

- Parser 片段构建默认 `quality-v2`；
- `--candidate-profile legacy` 可从历史数据集构建对照片段；
- embedding 不再直接读取 AST 数据集，也不在模型调用前临时切分；
- 片段模型名或 token 预算与 embedding 不一致时直接失败；
- 评价器检测 v2 根后使用 quality-v2，并能把 `semantic_slice` 映射为其字节范围内的 AST 节点；旧数据继续使用原规则；
- `recovered_function` 留在 Parser 数据集中作为证据，但不进入默认候选。

旧代码如果假设 `code_snippet` 已删除注释，必须显式迁移；静默恢复旧清洗会破坏原始映射合同。

## 规模与性能风险

quality-v2 产生 97,562 个原始候选，旧规则为 21,741 个。UniXcoder 的 Parser
长度治理排除或替换超限项后产生 96,039 个 model-ready 候选。增加来自真实函数根、
正确语句边界和语义核心，不是重复复制同一范围；同一文件、范围、粒度和来源
会去重。

Parser 片段构建需要读取 576 MB AST pickle、缓存候选文本并执行约 36.8 万个
唯一文本的 tokenizer 计数；当前 `fragments.pkl` 约 46 MB。完整 UniXcoder
嵌入的运行时间、内存和磁盘仍会高于历史全量实验。本轮只完成 Parser 全量运行、
tokenizer 全量审计和离线下游接口测试，没有运行完整模型嵌入，也没有触发 LLM。
运行正式嵌入前应：

- 固定语料提交和 candidate profile；
- 先统计候选数并估算批次数；
- 使用已有模型缓存和离线模式；
- 记录 `batch_size`、设备、耗时和峰值内存；
- 确认 `fragments.pkl` 的模型名、预算和数据集 SHA-256；
- 不把 `--max-regions-per-function` 或 `--max-statements-per-function` 的试验值伪装成默认结果。

Parser 本身全量耗时由 23.16 秒增至 34.89 秒，峰值 RSS 由 3.185 GB
增至 4.047 GB；pickle 体积下降 0.43%。如果在更大仓库出现内存压力，
优先把逐文件结果流式写入分片，再保持最终四列逻辑视图。

## 当前未解决清单

1. 原始 AST 覆盖率仍为 98.0380%，390,243 个非空白字节未可靠覆盖。
2. 宏影子只在 189 个文件启用，不提供真实宏展开语义。
3. `.h` 中 Objective-C/Objective-C++ 和生成语言片段仍会降低 C++ 解析质量。
4. 15 个 `recovered_function` 只有边界证据，不是可直接挖掘的干净候选。
5. Def-Use 没有类型、别名、控制依赖或跨过程信息。
6. 语义片段完全相同内容重复率为 1.20%；当前保留不同来源实例供聚类统计。
7. AST 数据集仍保留超长原函数和区域作为审计证据；它们不会进入对应模型的 `fragments.pkl`。1,310 条超长函数记录中有 85 条没有合格后备，只能保留拒绝证据。
8. 尚未在冻结人工标注集上测量精确率、召回率和误切分率。
9. 尚未对 96,039 个 model-ready 候选重新运行完整 UniXcoder、聚类和真实 Agent。

这些限制不影响当前“可检测、可统计、可追溯”的验收结论，但限制了对研究效果的外推。
