# C++ 实验数据集逐项目排查报告

## 排查口径

每个候选均检查公开可访问性、固定 commit、根目录许可证据、项目真实性、
非教学/非纯测试语料、C++ 主体、标准扩展名核心源码、领域与规模互补性，以及
在零构建条件下的实际 Tree-sitter 解析结果。项目状态还纳入 2026-07-29 的
阶段2聚类质量与具体簇语义复核。Parser 定量值来自
`outputs/dataset-experiment/final/<项目>/analysis.json`，不从 README 宣传
数字推断；聚类排除证据见 `cpp-clustering-quality-screening.md`。
正式 23 仓的统一分类口径见 `cpp-dataset-classification.md`。

“可靠 AST 字节覆盖率”按 Tree-sitter 中未落入 ERROR/MISSING 区域的显著源码字节计算。它是诊断指标，不代表项目可构建性或完整语义正确率；本轮没有构建目标项目。

## 逐项目过程证据

`cpp-dataset-manifest.json` 的每个项目条目都保存以下逐项目证据：

- GitHub 选择来源、公开 URL、主要语言、star、fork、仓库大小、创建/更新/push 时间和归档状态；
- 本地路径、远程 URL、完整 commit、commit 日期、浅克隆状态、许可文件与 SHA-256；
- 普通或稀疏源码根、实际构建文件样本、扩展名和统一排除规则；
- 固定 commit 的完整初始化、fetch、checkout 与 sparse-checkout 命令；
- 修改前基线和修改后分析命令、标准 `repo2data` 命令及产物路径；
- 基线/最终文件、代码行、函数、实体、候选、关系、错误、输出完整性、耗时、峰值内存和确定性摘要；
- 项目类型、C++ 标准、构建系统、习语重点、最终状态、判断理由与限制。

命令采用相同参数合同但每个项目都有自己的 slug、固定 SHA 与输出目录，因此不存在使用 basename 生成输出文件而相互覆盖的情况。完整逐文件失败原因和排除记录不重复嵌入本报告，而由每个项目的 `analysis.json` 与 `dataset.audit.json` 保存。

本轮没有项目专用 Parser 分支。扩展名补齐、目录段清洗、生成/测试文件规则、符号链接与越界拒绝、仓库相对路径身份及精确 `--project` 入口统一应用于 27 个候选；每行的“基线→最终”即该通用修改在对应项目上的复测范围。

## 分类与选取合理性

逐项目 `project_type` 保留细粒度用途，正式数据集另增加互斥 `primary_domain`，
用于在结果阶段复算领域宏平均。主领域只取项目核心交付用途；例如 `mosh` 归入
网络与分布式系统，`qbittorrent` 归入应用与跨平台界面，其网络属性仍由
`project_type` 和 `idiom_focus` 保留。这样既避免一个仓库重复进入同一分层汇总，
也不把交叉领域信息抹去。

相对分析复杂度不由人工印象决定，而是从清单中的有效代码行、核心文件和阶段1
候选数自动计算。三个指标先转为正式 23 仓内的平均秩百分位，再等权合成并近似
等频划分为低 8、中 8、高 7。该值表示流水线处理负荷，不表示代码质量、维护难度
或圈复杂度，也不会改变任何仓库的聚类或 LLM 配置。

候选选择采用目的性最大差异抽样：以真实性、C++ 主体、许可、活动性、标准源码
入口、领域与规模互补性建立候选池，随后分别通过阶段1可复现性审计和阶段2语义
适用性审查。它的优势是能够覆盖真实且差异较大的工程环境，限制是不能提供 GitHub
C++ 总体的概率代表性。正式报告因此必须同时给出 23 仓逐仓结果、仓库宏平均和
预先记录的分类分层结果，不能只选择有利仓库或类别。完整方法、逐仓分类和交叉
分布见[数据集分类与选取方法](cpp-dataset-classification.md)。

## 条件保留项目

### Catch2

Catch2 不是练习或样例集合，而是生产级测试框架本体。它对宏接口、模板、异常和类型擦除有独特覆盖；为避免测试语料主导数据集，只纳入框架核心并排除自测、示例与基准目录。

### concurrentqueue 与 magic_enum

两个项目的核心文件数分别为 7 和 9，但属于真实高复用库。concurrentqueue 提供
无锁并发与内存序，magic_enum 提供 C++17 编译期反射。它们用于习语多样性，
不用于规模代表性。

### Envoy 与 React Native

两个原有种子项目都以固定 commit 重建。为控制磁盘和分析边界，Envoy 只包含 `source`、`envoy`、`contrib` 与 `mobile/library/common`，React Native 只包含 `packages/react-native/ReactCommon`。清单记录了稀疏路径和复现命令；论文与报告不得把这些统计描述成完整上游仓库。

### nlohmann/json 与 Yoga

两个项目均是真实成熟项目，许可和核心代码规模合格，但可靠 AST 字节覆盖率
分别为 34.9% 与 38.9%。主要风险是宏、平台条件、聚合源码和现代泛型语法在
零构建 Tree-sitter 解析中的恢复区域较多。它们被保留以避免把 Parser 易处理性
误当作项目质量，但使用时必须报告覆盖率并结合逐文件错误类别。

## 阶段2后排除项目

### cpp-httplib

大型聚合头文件在未展开宏和条件编译时仅有 2.9% 可靠 AST 字节覆盖率，且阶段2
的 588 个簇中有 582 个局限于单文件，跨文件簇仅 6 个。代表代码仍包含网络、
回调和资源管理语义，因此它作为单头文件边界案例保留，但不满足主数据集的跨文件
复现测量要求。

### entt

942 个簇中 719 个是源码完全重复簇，9,100 个簇内成员中 79.0% 来自
`single_include/`。聚类主要重现模块化源码与单头文件发行版的镜像关系，不进入
后续 LLM 或主结果。

### simdjson

1,031 个簇中 956 个是源码完全重复簇，11,554 个簇内成员中 83.9% 来自
`singleheader/`。聚合源码、发行副本和依赖镜像主导结果，不进入后续 LLM 或
主结果。

## 淘汰项目

### Microsoft GSL

GSL 许可明确、活跃且领域相关，但其公开核心头文件按设计没有扩展名。排除 tests 后，扫描器在标准扩展名范围内得到 0 个核心文件，因此不满足本轮数据入口合同。该结论不会推动 Parser 为单一仓库加入路径特例；若未来研究决定支持无扩展名 C++ 头文件，应先建立通用的内容识别、误报控制和安全测试，再重新评估。

## 质量与安全检查

27 个候选的最终分析均为有效 JSON，正式 23 仓的 7,505 个扫描文件全部产生
文件记录且无解析失败。最终语料没有符号链接输入、路径越界或重复仓库相对路径。
清单校验还会读取三个“阶段2后排除”仓库，因此共核验 26 份标准 `dataset.pkl`
和 `dataset.audit.json`；它们的函数总数和扫描文件数均与独立统计一致。

机器可读的逐项目完整信息位于 `cpp-dataset-manifest.json`，其中还包括 GitHub 元数据快照、完整 commit、commit 日期、远程 URL、许可文件 SHA-256、源码范围、排除规则、复现命令、基线/最终解析指标和产物位置。
