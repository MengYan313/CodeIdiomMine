## 摘要

代码习语是开发者在特定语言和工程环境中反复采用的、具有明确语义且可复用的细粒度代码模式。高质量代码习语可以服务于代码理解、代码推荐、单元测试生成和编程规范检查。然而，现有方法往往依赖预定义规则或纯结构频率，难以同时兼顾候选覆盖、非连续语义关系、实现成本和工具可移植性，也难以区分“高频代码”与“值得复用的优质习语”。针对上述问题，本文将 CIMAS-CPP 组织为四阶段流水线：阶段1完成数据采集与清洗、AST构建与进阶处理、双轨代码片段抽取和元数据组装，其中轨道A保留语句级、区域级和函数级的大规模基础候选，轨道B只对存在明显跨边界 Def-Use、控制或显式资源配对关系的候选进行有界扩展，形成轻量 C++语义依赖链（Lightweight C++ Semantic Dependence Chain, L-CSDC）；阶段2融合代码语义嵌入、AST结构特征和可选依赖摘要，并用密度聚类发现候选簇；阶段3进行簇后对齐、AST反统一和差异元素抽象；阶段4由语义分析、语法逻辑和代码异味审查三个独立 Agent 并行评审，经综合判定后执行规划合成、代码组装、回流复审和静态验证，最终形成习语模板知识库。主实现优先使用 Clang 的类型、符号和 CFG 信息，同时通过统一适配层使大部分流程能够降级到 Tree-sitter。全流程只使用静态源代码分析，不要求运行程序、动态链接、测试执行、运行时插桩或复杂 LLVM IR 映射。评价以Haggis-CPP、纯LLM和内部消融为对照，不穷举整个仓库中的真实习语；公共自动指标覆盖全部输出，人工只核验跨方法去重后的统一Top-$K$结果池并派生质量校正指标。本文所有预期效果均需由真实实验验证。

**关键词：** C++；代码习语；代码异味；代码挖掘；抽象语法树；代码表征；密度聚类；大语言模型

## 1 引言

大型软件仓库不仅包含具体业务实现，也沉淀了大量经过长期实践形成的编程知识。例如，资源申请与释放、空指针防护、错误码传播、作用域锁管理、智能指针构造和容器遍历等逻辑，往往以相似但不完全相同的形式反复出现。这些模式具有比单个语句更丰富的语义，同时又比设计模式更细粒度，适合被抽象为代码习语。

自动挖掘代码习语面临三个核心困难。

第一，**重复不等于习语，高频也不等于优质**。自动生成的 getter/setter、日志样板和偶然复制的代码同样可能高频出现；更严重的是，不安全资源管理、吞掉异常、错误的生命周期处理等反模式也可能因复制传播而高频出现。若系统只依据频率和相似性学习，会把坏习惯包装成可推荐习语，产生“自动学习并放大反模式”的风险。

第二，**C++结构复杂且上下文敏感**。宏展开、模板实例化、函数重载、RAII、隐式类型转换等机制使 token 相似度难以准确表达代码含义。若只分析词法序列，变量重命名和等价 API 调用可能掩盖同一习语；若只分析 AST 结构，又可能把语义不同但形状相似的片段聚为一类。

第三，**候选边界与候选产量需要平衡**。固定语句、区域和函数切片简单、稳定且产量高，但可能漏掉非连续的定义—使用、检查—处理或显式获取—释放关系；若要求每个候选都满足复杂依赖闭包，又会显著提高实现成本并过滤大量本可用于聚类的样本。IdioMine 的 DCC 说明依赖关系适合补充非连续片段，但本研究不把所有候选改造成依赖链，而采用“固定三层保底、轻量依赖链增量补充”的双轨设计。

为此，本文提出 CIMAS-CPP。核心思想是使用 Clang 静态分析提供结构和语义基础，使用代码表征模型刻画功能相似性，使用密度聚类从大规模候选中发现自然簇，再通过 AST 模板抽象、多维专项评审、受约束合成和静态验证形成高质量习语库。本文不追求将全部工作交给大模型完成，而是让确定性工具负责大规模解析与验证，让表示学习和大模型集中处理结构规则难以覆盖的语义任务。当前语义、语法逻辑和代码异味专项评审的初始实现由独立 Agent 调用 LLM 完成，并通过结构化输出、固定提示、确定性证据和人工标注集检验其可靠性。

本文拟回答以下研究问题：

- **RQ1：** 在不构造全仓习语Ground Truth的条件下，CIMAS-CPP最终输出能否比传统Haggis-CPP、直接LLM和简单AST频率基线获得更好的覆盖—复现平衡、人工确认率、有效习语产量、静态有效性与成本权衡？
- **RQ2：** 在不降低基础候选产量的前提下，L-CSDC 能否补充固定三层切片漏掉的非连续 C++习语？Clang增强实现与Tree-sitter降级实现之间存在多大质量、覆盖和成本差异？
- **RQ3：** 挖掘到的习语能否跨仓库复现，并支持单元测试生成和编程规范识别等下游任务？
- **RQ4：** 相比单一LLM判定，语义、语法逻辑和代码异味的独立多Agent评审与综合裁决能否降低反模式泄漏和错误判定？合成回流复审与静态验证能否减少不可实例化或语义不完整的合成模板？

本文的预期贡献如下：

1. 提出由“数据与片段表示—嵌入与聚类—模板抽象—多Agent判定与合成”构成的四阶段 C++代码习语挖掘流水线，明确各阶段输入、输出和可替换边界；
2. 在阶段1提出产量约束的双轨候选抽取方法及 Clang优先、Tree-sitter可降级的统一适配层，以“固定三层保底 + 轻量静态依赖增量增强”平衡候选规模、人工确认的非连续增量与工程成本；
3. 在阶段2与阶段3结合结构—语义嵌入、密度聚类、簇后对齐、AST反统一和差异元素抽象，形成带绑定与前置条件的候选模板；
4. 在阶段4提出职责隔离的多Agent编排，由语义、语法逻辑和代码异味三个专项Agent并行评审，综合判定Agent裁决，再由规划合成与代码组装Agent生成并回流复审；
5. 建立不依赖全仓习语Ground Truth的分层评价体系，以Haggis-CPP和LLM-Direct为端到端基线，以七项公共自动指标覆盖全部输出，并通过跨方法去重的Top-$K$盲评池获得最小人工质量证据。

## 2 背景与相关研究

### 2.1 代码习语与代码克隆的区别

代码克隆关注两个或多个代码片段在文本、语法或语义上的相似关系，而代码习语还要求模式具有明确意图、一定频率和可复用性。克隆检测可以提供候选，但不能直接判断某个重复片段是否代表优质实践；被复制传播的缺陷或反模式也可能形成高支持度克隆簇。本文把“高频相似”视为候选发现线索，把“不含明显代码异味、语义清晰、可参数化、可验证”作为进一步约束。

### 2.2 预定义习语识别

规则驱动方法先定义目标习语，再通过 AST 查询、数据流规则或重构规则匹配实例；Pythonic idiom自动重构是这一封闭规则路线的代表[E017]。这类方法精度高、解释性强，但只能识别已知模式，且为 C++模板、宏和项目特定 API 编写规则的成本较高。本文关注开放式发现，即不预先限定具体习语名称。

### 2.3 数据驱动习语挖掘

Haggis 使用概率树语法挖掘重复结构，展示了从语法树中自动发现代码模式的可行性[E002]。IdioMine 进一步从 Java 函数的 AST 和 CFG 构造精简 PDG，并以变量Def/Use和必要控制结构形成 DCC 子习语[E006]，能够覆盖部分非连续源码行。其代价是依赖构建和路径处理更复杂，且单变量链仍会漏掉无共享变量的关联片段。本文只吸收“静态依赖可补充非连续候选”的思想，以局部Def-Use、控制和显式API配对形成L-CSDC，并保留原三层候选作为主要输入。

### 2.4 代码表征与大模型辅助分析

预训练代码模型可以将变量命名、API调用和控制结构映射到连续向量空间，为语义相似检索和聚类提供基础[E037]。大语言模型还可以解释代码意图并判断片段是否具备完整语义。然而，直接让大模型扫描整个仓库成本高、可复现性弱。本文采用“静态分析和聚类初筛，大模型后置精判”的混合策略。

### 2.5 代码异味检测与反模式过滤

代码异味是潜在劣质设计或实现的风险信号，相关研究已形成分类学、规则/度量检测、历史分析、机器学习和工具组合等路线。Mäntylä 等较早建立了代码异味分类[E040]，DECOR 将异味描述转化为可执行检测规则[E070]；系统综述则指出，异味定义具有主观性，检测器容易受规则阈值、覆盖范围和误报影响[E055][E079][E078]。经验研究还给出两项对本课题尤其重要的结论：异味可能在实体创建时即被引入并长期存留[E036]，但异味标签与维护成本之间并非在所有设置下都有稳定关系[E069]。因此，本研究把异味作为习语入库前的风险过滤依据，而不是把任何异味标签自动等同于缺陷或绝对低质量。

机器学习检测能够减少部分手工阈值依赖，但高度依赖标签、类别平衡和项目分布[E080][E078]。代码自然性研究发现缺陷代码总体上更可能表现出较高熵[E056]，却不能排除被复制传播后变得高频、可预测的坏习惯。C++ 侧的 CLEAN++ 已利用 Clang AST 和编译数据库实现35类规则型异味[E028]，说明确定性 C++ 检测可作为本研究的对照和后续补充；其预定义类别和阈值也难以覆盖全部项目语境。ASE 2024 的 iSMELL 显示，将 LLM 的语义能力与专家工具结合优于直接使用 LLM 的基线[E027]，支持本研究采用独立审查模块并保留未来工具融合接口。

基于上述证据，本研究当前首先实现 Code Smell Review Agent 调用 LLM 的审查关卡，并将其明确视为需要实验验证的初始方案。审查采用 `pass`、`reject`、`manual_review` 三路分流；高置信严重异味拒绝，依赖语言标准、项目约定或上下文的边界样本进入人工复核。实验必须与无审查、普通 LLM 附带异味判断、CLEAN++/其他静态规则以及 Agent+人工复核比较，同时报告漏报和误过滤，避免质量过滤本身成为新的系统性偏差。

## 3 问题定义

给定一个 C++仓库集合 \(R=\{r_1,r_2,\ldots,r_m\}\)，静态分析器从每个仓库中抽取候选片段集合 \(S_r\)。每个候选片段 \(s\) 由以下信息组成：

\[
s = \langle code, ast, level, context, location, dep, backend, capability, source \rangle
\]

其中，`code` 和 `ast` 为源码与AST视图，`level` 为语句/区域/函数粒度，`context` 与 `location` 保存上下文和连续或非连续位置，`dep` 为可选的轻量静态依赖摘要，`backend` 标记 Clang 或 Tree-sitter，`capability` 标记该后端实际提供的类型、符号、CFG等能力，`source` 标记候选来自基础轨道还是增强轨道。缺失高级语义信息不会使基础候选失效。

目标是学习一个习语集合 \(I\)。每个习语 \(i\in I\) 包含参数化模板、实例集合、语义描述、适用前置条件和质量分数：

\[
i = \langle template, instances, intent, precondition, quality \rangle
\]

一个有效习语应满足：

1. 在仓库中出现次数不低于频率阈值；
2. 实例具有相近结构或功能；
3. 模板能够通过参数实例化恢复合法 C++代码；
4. 习语具有可描述的编程意图；
5. 习语不应主要由项目特有常量或无意义样板构成；
6. 习语不包含经审查确认的明显代码异味或应当拒绝复用的反模式。

## 4 CIMAS-CPP 方法

### 4.1 总体流程

```text
C++仓库
  → 阶段1：数据采集/清洗 → AST构建与进阶处理
           → 双轨代码片段提取 → 元数据组装
  → 阶段2：Embedding嵌入 → HDBSCAN聚类与代表簇筛选
  → 阶段3：簇后清洗/对齐 → AST反统一 → 差异元素抽象
  → 阶段4：语义/语法逻辑/代码异味多Agent评审
           → 综合判定 → 规划合成 → 代码组装
           → 合成结果复审 → 静态验证 → C++习语模板知识库
```

上述四阶段是 CIMAS-CPP 后续实现、实验、消融和论文写作的固定上位基准。阶段内部的解析器、嵌入模型、聚类器或Agent实现可以替换，但除非有新的实验证据和用户明确调整，不应改变“表示构建—聚类发现—模板抽象—多Agent判定与合成”的阶段边界和顺序。

### 4.2 阶段1：数据与习语表示构建

本研究吸收 IdioMine“利用依赖补充非连续语义片段”的思想，但不以完整 PDG 或复杂路径分析替换原三层抽取。核心原则是：基础候选负责覆盖，轻量依赖候选负责增量创新；增强失败时仍保留基础候选，不能因为缺少高级语义信息而丢失样本。

#### 4.2.1 数据采集、清洗与解析后端

系统从固定 commit 的 C++仓库采集源码、构建文件和可用的 `compile_commands.json`，记录仓库、模块、文件路径、语言标准和编译数据库覆盖状态。清洗阶段识别自动生成文件、第三方依赖、副本文件、空函数、机械 getter/setter 和极端长度片段；是否排除测试代码、示例代码和外部依赖必须作为显式配置，并保存清洗前后文件数、代码行数和排除原因，避免只保留最终百分比。

系统定义与具体解析器解耦的最小接口：AST节点类型、源码范围、父子关系、函数/块作用域、声明与使用位置、控制结构包含、调用表达式和原始类型文本。Clang 是主实验后端；当项目难以生成完整编译数据库或需要快速部署时，可使用 Tree-sitter 后端。

| 能力 | Clang主后端 | Tree-sitter降级后端 | 对候选的影响 |
|---|---|---|---|
| AST节点、源码范围、作用域 | 精确 | 支持 | 三层基础候选均可生成 |
| 语句/区域/函数识别 | 精确 | 支持 | 主流程保持一致 |
| 符号绑定与类型 | 语义解析 | 名称和类型文本近似 | 影响聚类特征，不删除候选 |
| 控制关系 | 可使用函数内CFG | 词法嵌套与语句顺序近似 | L-CSDC精度可能下降 |
| 局部Def-Use | 按声明绑定 | 按名称+最近可见声明近似 | 降级结果单独标记 |
| 宏、模板、隐式析构 | 可保留来源或补充标签 | 仅保留可见语法 | 作为可选增强，不是主流程前提 |

每个候选保存 `backend` 和 `capability`。Clang用于完整端到端主实验；Tree-sitter主要在按普通源码、宏密集、模板密集和缺失编译数据库分层抽取的文件子集上评价候选抽取与表示保持率，不强制重复全部LLM审查和下游实验。不能把 Tree-sitter 的近似依赖写成 Clang 等价语义。

#### 4.2.2 AST进阶处理与双轨片段抽取

AST构建后执行节点规范化、作用域恢复、函数/控制区域定位、源码范围映射和重复AST哈希。Clang后端额外恢复符号绑定、类型和函数内CFG；Tree-sitter后端使用名称、最近可见声明、词法嵌套和语句顺序近似。随后执行双轨抽取。

**轨道A：固定三层基础候选。** 该轨道延续原方案并始终执行：

- **语句级**：声明、赋值、调用、返回、抛出和显式资源操作；
- **区域级**：条件、循环、`try/catch`、lambda、连续调用链和词法作用域；
- **函数级**：长度受控的完整函数或方法。

该轨道只使用宽松、可复现的清洗规则去除自动生成文件、空函数、机械 getter/setter 和极端长度片段。它不要求依赖闭合、编译数据库完整或高级类型推断，从而保持与原方法相近的候选规模。三类候选是正式方法的一部分，而不是只作为基线。

**轨道B：选择性轻量L-CSDC。**

轨道B只在函数内使用静态源代码信息，对下列候选尝试增强：某个局部实体的定义和使用跨越基础边界；条件检查与后续处理被无关语句隔开；两个显式调用通过同一局部实体形成获取—使用—释放、加锁—解锁或打开—关闭关系；区域内部存在可由同名/同符号实体连接的非连续语句。

轻量依赖图只包含：

\[
G_f^{light}=(V,E_{order},E_{scope},E_{du},E_{ctrl},E_{pair})
\]

其中各边分别表示源码顺序、词法作用域、局部 Def-Use、控制包含/函数内CFG关系，以及由小型可配置 API 表识别的显式配对关系。初始配对表只覆盖少量可明确验证的 C/C++ 写法，例如 `fopen/fclose`、`malloc/free`、显式 `new/delete`、`lock/unlock`；配对必须作用于同一局部实体，规则表需版本化并在附录公开。Clang 后端可用符号绑定、类型和 CFG 提高精度；Tree-sitter 后端使用名称、最近可见声明、词法嵌套和语句顺序近似同一过程。

L-CSDC 从一条基础语句或区域出发，只补入最多两跳依赖、一个必要控制头和有限数量的关联语句；每个锚点最多生成一个增强候选，节点数不得超过对应函数的固定比例和绝对上限。系统不枚举执行路径，不进行动态分析、运行时插桩、动态链接、跨过程指针分析、LLVM IR/MemorySSA映射或全程序别名求解。指针别名、隐式析构、异常栈展开和未知调用副作用仅作为 Clang 可提供时的标签，不作为生成 L-CSDC 的强制条件。

#### 4.2.3 候选合并、元数据与产量约束

最终候选集合为：

\[
S=S_{base}\cup S_{enhanced}
\]

其中 \(S_{base}\) 为轨道A全部基础候选，\(S_{enhanced}\) 为轨道B成功生成的补充候选。两轨通过规范化源码、AST类型序列和位置集合联合去重；当增强候选与基础候选等价时，只合并元数据，不重复计数。L-CSDC 失败、依赖不确定或 Tree-sitter 出现语法恢复误差时，仅放弃该增强候选，不删除其来源基础候选。

非连续增强候选按原始源码顺序重建，并补入最小控制头和作用域骨架；被省略的语句记录为 `<HOLE_n>` 元数据。每个候选组装统一元数据：源码/AST视图、粒度、基础/增强来源、仓库/文件/函数位置、解析后端、能力掩码、自由变量、类型文本、轻量依赖摘要、宏/模板标签、规范化哈希和清洗记录。L-CSDC 后续不要求每个候选都具有完整依赖图。

方法是否可行首先由候选产量和成本约束，而不是由图的复杂程度决定：

- 基础候选保留率相对原固定三层实现应接近100%；差异只能来自统一记录的清洗和去重规则；
- 不以依赖闭合度作为基础候选硬过滤条件；
- L-CSDC 增强候选数量、抽样边界有效率，以及最终形成的人工确认非连续习语增量单独报告；
- 报告每千行代码的解析时间、峰值内存、基础候选数和增强候选数；
- 若 L-CSDC 的抽样边界有效率或人工确认增量不足以抵消成本，则缩小适用触发器，而不是继续增加依赖类型。

因此，本研究把创新点进一步表述为“产量约束的依赖增强”。在开发集上选择触发规则和预算，使

\[
J=VNG_{norm}+\mu\,EVY_{sample}-\lambda\,EC_{norm}
\]

最大，其中 $VNG$（Validated Non-contiguous Gain）表示开发集上由轨道B独有贡献、且经人工确认的非连续最终习语数（按每万行代码归一化），$EVY_{sample}$ 只在分层抽样的L-CSDC候选上评价边界合理率。该目标同时要求基础候选全部进入合并前集合，并限制增强候选数不超过基础候选数的固定比例。它不假设能够获得全仓库习语真值，只用于在人工确认增量、抽样候选有效率和工程成本之间选择可复现配置；测试集不参与规则与预算选择。

### 4.3 阶段2：Embedding嵌入与Cluster聚类

所有基础候选都计算语义向量 \(e_s\) 与 AST结构向量 \(a_s\)：

\[
z_s^{base}=\operatorname{Norm}([\alpha e_s;(1-\alpha)a_s])
\]

语义向量由预训练代码模型编码规范化源码得到；结构向量使用两个后端均能提供的 AST节点类型、路径、控制结构计数和调用/声明比例。这样即使只有 Tree-sitter，也可运行完整的候选聚类主流程。

对 L-CSDC 或 Clang 能提供额外信息的候选，再计算轻量依赖摘要 \(d_s\)，包括链长度、Def/Use数量、控制头数量、显式API配对和非连续跨度。依赖摘要作为附加特征或重排信号，并与 `capability` 掩码共同输入，避免把“缺失能力”误解为“依赖不存在”。论文通过消融决定该摘要是否进入最终表示；若收益不稳定，则只保留其作为候选来源元数据。

#### 4.3.1 密度聚类、代表实例与簇级元数据

本文采用 HDBSCAN 发现密度簇。该方法不要求预先指定习语数量，能够在层次化密度结构中选择稳定簇，并把孤立片段作为噪声过滤[E051]。候选首先按语句、区域、函数和L-CSDC四种来源分层聚类，避免尺度差异；随后用统一基础表示执行跨来源近邻检索，识别基础候选与增强候选是否表达同一模式。`min_cluster_size`、`min_samples` 和簇选择策略在验证集上确定，测试集不参与调参。

对每个簇 \(C\) 计算候选质量：

\[
Q(C)=\lambda_f F(C)+\lambda_c Coh(C)+\lambda_r Rep(C)+\lambda_x XRepo(C)
\]

其中，\(F\) 表示出现频率，\(Coh\) 表示簇内内聚度，\(Rep\) 表示跨文件重复程度，\(XRepo\) 表示跨仓库复现信号。该分数只衡量候选簇是否值得进一步审查，不代表代码质量；低于阈值的簇不进入昂贵的代码异味审查和语义判定阶段。

### 4.4 阶段3：簇后处理、AST反统一与差异元素抽象

聚类输出不直接进入LLM。系统先在簇内按源码、AST规模、能力掩码和轻量依赖摘要进行二次对齐，剔除明显偏离簇中心且无法与公共AST骨架对齐的实例，并保留被剔除实例及理由。随后使用 AST 反统一寻找最小公共结构。节点类型和绑定关系一致的部分保留，差异节点根据语义类别替换为占位符：

- `<TYPE_n>`：类型；
- `<VAR_n>`：变量或成员；
- `<LIT_n>`：字符串、数值、枚举等字面量；
- `<CALL_n>`：可替换的函数或方法调用；
- `<EXPR_n>`：结构允许变化的表达式；
- `<BLOCK_n>`：可插入的语句块。

同一占位符在模板中多次出现时保持绑定一致。例如，资源创建和释放位置使用同一个 `<VAR_1>`，从而保留显式数据关系。L-CSDC 候选可用其 Def-Use 和显式配对角色辅助对齐；基础候选仍可仅依赖 AST 反统一，不因缺少依赖摘要而被排除。

阶段3输出的不是最终习语，而是候选模板对象，包括公共AST骨架、占位符及绑定关系、代表实例、簇支持度、跨文件/跨仓库来源、适用上下文、能力掩码和已知前置条件。频率与簇内一致性只证明模板值得进入评审，不能代替阶段4的质量判定。

### 4.5 阶段4：LLM多Agent习语判断与合成

阶段4参考“专项评审—综合裁决—规划合成—代码组装—回流复审”的协作方式。语义、语法逻辑和代码异味由三个职责独立的 Agent 并行判断，综合判定 Agent 只汇总结构化证据并执行预定义裁决规则；通过判定的原始模板可直接进入静态验证，其中满足轻量静态关系触发器的模板再交给规划合成 Agent 和代码组装 Agent。合成结果必须重新进入同一评审链，不能直接写入知识库。LLM只处理阶段3筛出的簇级模板而非全量代码片段，且规划与组装只作用于通过评审的可合成子集，以限制调用规模。

```text
阶段3候选模板
   ├─→ 语义分析Agent ───────┐
   ├─→ 语法逻辑Agent ──────┼─→ 综合判定Agent
   └─→ 代码异味审查Agent ──┘       │
                         pass ──────┼─→ 有效习语模板
                         reject ────┼─→ 拒绝日志
                         review ────┘─→ 人工复核
                                      │
                               规划合成Agent
                                      ↓
                               代码组装Agent
                                      │
                    ┌──── 合成结果回流三类专项评审 ────┐
                    └─通过→静态验证→习语模板知识库─────┘
```

#### 4.5.1 三类专项评审Agent

- **语义分析 Agent（Semantic Analysis Agent）**：判断模板是否具有单一且可描述的意图、语义完整性、通用性、复用价值和明确前置条件；拒绝纯样板、过度项目化或意图不完整的模式。
- **语法逻辑 Agent（Syntax and Logic Agent）**：结合AST骨架、占位符绑定、局部Def-Use、控制关系和解析器结果，检查语法结构完整性、变量绑定一致性、控制/数据逻辑连贯性和可实例化风险。解析器错误以及已获得的 `clang++ -fsyntax-only` 结果属于确定性证据，LLM不能覆盖工具错误。
- **代码异味审查 Agent（Code Smell Review Agent）**：独立识别不安全资源管理、异常吞噬、空指针/悬空引用风险、并发与锁风险、不可达/无效逻辑、魔法值和过度复杂控制等潜在反模式。异味结论是风险判断，不等同于缺陷真值，也不能被语义评分抵消。

三个 Agent 接收同一候选模板、代表实例、簇统计和必要上下文，但使用不同的固定 prompt 与输出 schema，且相互不可读取对方结论，以降低职责混合和相互迎合。以下为代码异味审查输出示例：

```json
{
  "has_code_smell": true,
  "smell_types": ["resource_management"],
  "severity": "high",
  "confidence": 0.91,
  "evidence": ["资源获取后存在未覆盖的提前返回路径"],
  "decision": "reject",
  "reason": "该高频模式可能传播资源泄漏，不应作为习语复用"
}
```

代码异味审查自身输出 `pass`、`reject` 或 `manual_review`，但不直接决定候选的最终去向：高置信严重异味构成综合裁决的拒绝证据，低置信或依赖项目约定的风险进入人工复核。为保证可复现性，应固定各Agent的模型版本、系统提示、分类表、温度、最大重试次数和输出 schema，并保存每次输入、输出和人工裁决。该阶段不宣称 LLM 能替代静态分析器或专家，后续可增加 Clang-Tidy 等确定性工具作为证据源或对照。

#### 4.5.2 综合判定Agent与裁决规则

综合判定 Agent（Comprehensive Judgment Agent）接收三个专项报告，只负责检查证据完整性、处理冲突并执行预定义规则，不重新扮演三个专家，也不能用较高的语义评分覆盖语法错误或严重异味。为控制复杂度，无冲突样本由schema校验和确定性门槛直接裁决；仅在报告冲突、证据不足或上下文依赖时调用LLM完成解释与人工复核路由。因此“综合判定Agent”是统一裁决职责，不意味着每个候选都额外发起一次模型调用。其结构化输出至少包含：

```json
{
  "semantic_status": "pass",
  "syntax_logic_status": "pass",
  "smell_status": "pass",
  "decision": "pass",
  "conflicts": [],
  "preconditions": ["C++17及以上"],
  "reason": "意图完整、绑定一致，且未发现高置信严重异味"
}
```

裁决遵循显式门槛：语义和语法逻辑均为 `pass`，且代码异味为 `pass` 时，候选才进入有效习语集合；任一确定性解析/语法验证失败，或任一专项报告给出高置信严重风险时，候选进入 `reject`；报告缺失、专项结论冲突、置信度处于边界区间或风险依赖项目语境时进入 `manual_review`。被拒绝或转人工的候选保留各专项证据，避免把最终标签当成不可解释的单一LLM结论。

#### 4.5.3 规划合成Agent与代码组装Agent

通过综合判定的细粒度模板可能分别描述“获取资源”“检查失败”和“释放资源”。规划合成 Agent（Synthesis Planning Agent）只在以下静态关系至少成立一项时提出合成：同一函数或同一控制/异常区域、共享局部实体、显式Def-Use、显式API配对或稳定源码顺序。它输出参与模板、组合顺序、插入位置、占位符绑定、前置条件和预期完整意图，不直接生成代码。

代码组装 Agent（Code Assembly Agent）按照计划执行 AST感知的拼接、嵌套或占位符统一。合成后长度不得超过上限，不能引入未绑定符号，也不允许补写输入模板和代表实例中不存在的业务操作。L-CSDC 可提供部分合成关系；基础候选则使用函数/区域位置、共享实体、控制关系和源码顺序。若无充分静态关系、计划冲突或组装失败，系统保留原始细粒度习语，不强制合成。

#### 4.5.4 合成复审、静态验证与知识入库

每个合成结果都作为新的候选模板回流至语义分析、语法逻辑和代码异味审查三个专项 Agent，再由综合判定 Agent 裁决。回流次数设置固定上限；不允许 Agent 在失败后无界自我修复。只有回流复审通过的模板才执行以下静态验证：

- **回填验证**：用簇内真实实例的绑定回填占位符，要求能够恢复原始或等价 AST；
- **解析验证**：至少由当前解析后端重新解析；Tree-sitter降级实验以此为最低门槛；
- **可选Clang语法验证**：编译配置可用时，在保留必要 `include`、类型和命名空间的测试壳中执行 `clang++ -fsyntax-only`。

验证不执行链接、动态加载或程序运行。依赖项目私有类型、无法构建最小编译单元的习语记录为“上下文依赖型”，保留解析结果和未满足依赖，不因缺少完整构建环境而被错误判为语法失败。最终知识对象包括参数化模板、意图、适用前置条件、正反例、来源与支持度、三个专项报告、综合裁决、合成历史和静态验证状态；原始模板与合成模板均可入库，但必须能够追溯其证据链。

数据按文件或模块划分训练/开发/测试区域，避免同一近重复文件同时出现在调参集和测试集。跨仓库实验采用留一仓库测试：在三个仓库上形成习语库，在未参与挖掘的仓库中检验复现与匹配。

### 5.2 对比方法

评价分为端到端主对比、CIMAS-CPP内部消融和部署降级三层。端到端主对比只保留能够独立从训练代码产生习语模板的方法；阶段特有指标不参与主方法排名。

#### 5.2.1 端到端主基线

1. **Haggis-CPP。** Haggis把习语定义为带元变量的重复AST片段，以非参数贝叶斯概率树替换文法（DP-pTSG）学习能够解释训练语料的常见结构。原论文指出其统计方法原则上与语言无关，只要求目标语言能够提供语料和AST；但原实现使用Eclipse JDT及Java专用入口，因此本文实现的是面向C++的算法复现版本，而不是直接运行原Java工具[E002]。复现入口为[Haggis论文原文（作者主页PDF）](https://homepages.inf.ed.ac.uk/csutton/publications/idioms.pdf)和[原作者公开实现 `codemining-treelm`](https://github.com/mast-group/codemining-treelm)；后者已经归档，使用时应固定commit。具体做法是：使用Clang将训练区域转换为函数级AST森林，移除系统头文件和编译器隐式节点；以节点类型和简单属性构造文法符号，对多子节点属性执行与原论文一致的二叉化；将标识符包装为带可用类型信息的 `MetaVariable`；运行DP-pTSG采样并按后验支持度、最小出现文件数和最小节点数输出连接AST片段。该基线不使用Embedding、聚类、依赖增强、LLM判断、代码异味审查或习语合成。公开代码用于核对采样与后处理逻辑，但Clang适配、C++文法符号和实验脚本属于本文复现，必须公开差异清单。
2. **LLM-Direct。** 该基线不构造AST/CFG/L-CSDC，不计算Embedding，不聚类，也不执行AST反统一或多Agent编排。由于完整仓库无法直接放入单次上下文，只允许两项不可避免的机械操作：按文件和模型token上限把训练源码切成带少量重叠的原始文本块，以及对最终字符串执行精确去重。第一轮由同一个LLM从每个文本块直接输出代码习语模板、占位符、代表证据和简短意图；第二轮仍由同一LLM合并语义重复项并排序，形成仓库级结果。主实验使用与CIMAS-CPP阶段4相同的基础模型和近似总LLM token预算，记为 `LLM-Direct-Budget`；若经费允许，再运行覆盖全部训练源码的 `LLM-Direct-Full`，但必须单独报告其额外成本，不能与预算匹配结果混为一组。
3. **CIMAS-CPP。** 使用本文完整四阶段方法，作为待评价方法而非基线。

另保留 **AST-Frequent** 作为简单结构下界：统计规范化AST连接子树的跨文件支持度，按开发集阈值输出模板。它不替代Haggis-CPP，只用于判断复杂pTSG是否确实优于直接频率计数。IdioMine式DCC不作为主端到端基线，因为其Java PDG构造与ChatGPT合成难以在不重新设计的情况下完整迁移到C++；本文只在阶段1诊断中保留 `DCC-Style` 表示对照，并明确为自实现。

#### 5.2.2 公共输出契约与公平控制

所有主方法必须从相同训练区域独立输出统一对象：参数化C++代码模板、占位符与绑定、至少一个训练来源位置、方法自身的支持度/置信度和排序。公共适配器只允许完成字段映射、Clang重新解析、规范化哈希与精确去重，不能替基线补做语义合并、异味过滤、依赖分析或习语合成。对Haggis-CPP，适配器把pTSG片段直接序列化为占位符模板；对LLM-Direct，输出由固定JSON schema约束。

训练、开发和测试按近重复文件/克隆族分组后划分，所有方法在测试阶段只能使用训练所得模板和统一匹配器，测试源码不得进入LLM上下文或参数选择。Haggis的 `alpha`、最小支持和节点数，LLM提示及每块输出上限，CIMAS的聚类与筛选阈值均只在开发集使用Raw-F1和资源约束选择，不使用测试人工标签调参。

自动指标在每种方法经过开发集阈值和精确去重后的完整输出集合上计算。人工评价在实验前根据统一标注预算设定每仓库最大 $K$，各方法按自身训练期原生分数取Top-$K$，并在指标名中标注 `@K`；若各方法输出均不超过预算，则Top-$K$自然等价于全量核验。方法不足 $K$ 个结果时不得补齐。跨方法规范化后完全相同的模板合并成一个盲法标注项，标签复用于所有产生该模板的方法，以减少重复人工工作。

### 5.3 评价框架与指标

本研究不构造“整个代码仓库中全部真实习语”的Ground Truth，也不计算全仓习语Recall。为使Haggis-CPP、LLM-Direct、各消融变体和CIMAS-CPP能够公平比较，指标分为“全自动公共指标”“最小人工核验及派生指标”“方法内部诊断”三层。端到端结论只依据前两层，第三层只解释本文方法为什么有效。

#### 5.3.1 全自动公共指标

为与Haggis及CIMAS历史结果比较，所有方法首先在完整去重输出集合上计算以下指标：

- **Raw Idiom Coverage（Raw-IC）**：测试函数中被任一输出模板匹配的AST节点并集占比。重叠节点只计一次，并同时报告函数宏平均和节点微平均；宏平均作为主值。
- **Raw Idiom Set Precision（Raw-ISP）**：训练所得模板中在独立测试区域至少复现一次的比例。它表示集合复现性，不是人工正确率。
- **Raw-F1**：Raw-IC宏平均与Raw-ISP的调和平均，只表示覆盖—复现平衡。
- **Average AST Size（AvgAST）**：模板使用其训练代表实例回填后包含的AST节点数；同时报告中位数和四分位距，无法回填/解析的模板计入IV失败但不从输出数中删除。
- **Output Yield（OY）**：每万行有效C++训练代码产生的去重输出模板数，防止只比较比例而忽略方法实际产量。
- **Instantiation Validity（IV）**：用方法提供的训练证据回填占位符后，能够恢复匹配AST并由Clang重新解析的模板比例。可用编译上下文中的 `clang++ -fsyntax-only` 通过率另列，不强迫缺失构建配置的模板进入不公平分母。
- **End-to-End Cost（Cost）**：每万行代码的墙钟时间、峰值内存、CPU/GPU时长、LLM输入/输出token和按调用时价格计算的费用。非LLM方法的token与API费用记为0，不把不同资源强行压缩成一个不透明总分。

设测试函数 $f$ 的可统计AST节点为 $N_f$，输出集合 $I$ 在函数中匹配到的节点并集为 $M(f,I)$，则IC、ISP与F1仍按下式计算：

\[
IC_{macro}=\frac{1}{|F|}\sum_{f\in F}\frac{|M(f,I)|}{|N_f|},\quad
ISP=\frac{|\{i\in I\mid i\text{在测试区域复现}\}|}{|I|},\quad
F1=\frac{2\cdot IC_{macro}\cdot ISP}{IC_{macro}+ISP}
\]

当分母为空或IC与ISP均为0时，对应指标记为0。统一评估器使用Clang AST和预先固定的模板匹配规则；这只是测量工具，不算向Haggis或LLM基线额外提供程序分析能力。IC与ISP沿用Haggis及CIMAS历史评价思路[E002][E001]；CIMAS历史ANI1/ANI2仅表示两个下游任务的AST节点增幅，不进入端到端习语挖掘主表[E001]。[CIMAS-PAPER, p.2]

#### 5.3.2 最小人工核验与质量校正

人工工作只核验Top-$K$盲评池中的最终模板，不从源码中寻找漏掉的习语。每个跨方法精确去重后的模板只标一次，最小标签为：`valid_idiom`、`invalid_idiom` 或 `context_dependent`，以及是否含应阻止复用的严重代码异味。无效原因记录为意图不清、边界不完整、机械样板/过度特化、语法逻辑错误或严重异味。两名C++标注者独立评价，隐藏方法名称、原生分数和Agent结论，分歧由第三人裁决；报告Cohen’s Kappa、标注数量和用时[E095]。代码完整性、语义清晰度和泛化性的1—5分评价降为可选的分层定性分析，不再要求对所有输出评分。

人工标签只产生两个直接主指标：

\[
HVIP@K=\frac{|I_{valid}@K|}{|I_{out}@K|},\qquad
ALR@K=\frac{|I_{severe\_smell}@K|}{|I_{out}@K|}
\]

其中HVIP@K衡量Top-$K$输出中人工确认习语的比例，ALR@K衡量反模式泄漏。上下文依赖项在保守HVIP@K中不计为有效，并单独报告未决率。若全部输出少于 $K$，则对全部输出计算并注明“all”；若没有输出，HVIP@K记为不适用，其他产量和覆盖指标记为0。

同一组人工标签还可自动派生质量校正指标，无需新增标注：只用人工确认集合重新运行统一匹配器，得到 **V-IC@K、V-ISP@K和V-F1@K**；并计算 **Validated Idiom Yield（VIY@K）**：

\[
VIY@K=\frac{|I_{valid}@K|}{\text{有效C++训练代码行数}/10{,}000}
\]

Raw指标回答“方法自动输出了多少、覆盖和复现如何”，V指标回答“确认有效的那部分实际覆盖和复现如何”。二者必须并列报告，不能只展示对本方法更有利的一组。

#### 5.3.3 方法内部诊断与指标删减

以下指标不要求所有baseline计算，也不进入端到端主排名：阶段1报告自动化的BCR、PPR、抽取时间与内存，分层抽样的 $EVY_{sample}$，以及轨道B独有的人工确认非连续增量VNG；阶段4通过 `NoSmell` 消融的ALR@K变化验证异味审查贡献，并仅在少量pass/reject/manual_review审计样本上报告CS-P/CS-R/CS-F1和FRR。CRM作为留一仓库泛化的独立实验指标。

原计划中的DEP/DER、SD-F1、SL-F1和SRR不再列为论文主指标：它们分别需要额外边级或模块级真值，且Haggis与LLM-Direct无法对应计算。若实现调试确有需要，可保留在附录或日志中，但不得扩张人工标注任务。最终端到端主表固定为两组：自动组 `Raw-IC、Raw-ISP、Raw-F1、AvgAST、OY、IV、Cost`；人工及派生组 `HVIP@K、ALR@K、V-IC@K、V-ISP@K、V-F1@K、VIY@K`。

### 5.4 参数与实现记录

正式实验需记录公共数据划分、克隆族分组、AST纳入节点表、统一模板schema、匹配规则、精确去重规则、Top-$K$预算和全部指标分子分母。Haggis-CPP额外记录原代码版本、C++适配差异、Clang AST到TreeNode映射、二叉化/MetaVariable规则、MCMC迭代与burn-in、`alpha`、最小支持和最小节点数；LLM-Direct记录分块长度/重叠、map/reduce prompt、模型版本、温度、随机种子、每块输出上限、总token和失败重试；CIMAS-CPP记录Clang/Tree-sitter版本、编译数据库覆盖率、能力掩码、L-CSDC预算、嵌入/聚类参数、各Agent prompt/schema和回流上限。

所有方法统一保存完整输出、原生排序分数、Top-$K$子集、代表训练证据、重新解析/语法验证日志、墙钟时间、峰值内存、CPU/GPU时长、LLM token及费用。人工侧保存跨方法去重映射、盲法标签、标注时长、一致性和裁决记录。主流程及所有baseline均不得依赖动态执行、运行时插桩或项目动态链接环境。

### 5.5 实验执行与统计分析

端到端比较先在每个仓库内独立计算指标，再报告仓库宏平均，避免Envoy等大型仓库支配结论；节点微平均只作补充。确定性方法至少完整运行一次，含随机采样、聚类或LLM的方法使用不少于三个固定随机种子，报告均值、标准差和全部失败运行。LLM-Direct-Budget与CIMAS-CPP使用相同基础模型，并以实际输入加输出token校验预算差异，不能只以预估上限宣称预算匹配。

对Raw-IC、Raw-ISP、Raw-F1、IV等自动指标，以文件或克隆族为重采样单位计算配对bootstrap 95%置信区间[E076]；对HVIP@K、ALR@K等比例报告分子、分母及Wilson 95%置信区间[E092]。多方法比较先进行总体检验，再对预注册的“CIMAS-CPP对Haggis-CPP”“CIMAS-CPP对LLM-Direct-Budget”和核心消融差异执行配对比较，并用Holm方法校正多重检验[E022]。除显著性外必须报告绝对差值和相对成本，不构造把覆盖、质量和费用任意加权的单一总分。

## 7 案例分析

### 7.1 RAII锁管理习语

示例模板：

```cpp
{
    std::lock_guard<<TYPE_1>> <VAR_1>(<MUTEX_1>);
    <BLOCK_1>
}
```

该模板表达“在词法作用域内持锁并自动释放”的意图。合法性条件包括 `<MUTEX_1>` 与 `<TYPE_1>` 匹配，且 `<VAR_1>` 生命周期覆盖 `<BLOCK_1>`。相比仅挖掘构造语句，区域级模板保留了作用域边界。

### 7.2 资源获取与失败清理习语

```cpp
auto <VAR_1> = <CALL_1>(<EXPR_1>);
if (<VAR_1> < 0) {
    return <ERROR_1>;
}
// ...
<CALL_2>(<VAR_1>);
```

此类模板必须通过数据依赖确认获取、检查和释放操作使用同一资源变量。若项目可使用RAII替代手工释放，代码异味审查 Agent 应结合语言标准、项目约定和代表实例，把该模板标记为“项目约定型/需人工复核”，而不是无条件的最佳实践或直接拒绝。

### 7.3 高频但非习语的反例

单独的日志语句、默认构造函数、空异常处理和机械字段赋值可能非常高频。代码异味审查Agent应将空异常处理等明显反模式作为拒绝证据，语义分析Agent则应将缺少独立意图的机械样板作为拒绝证据；语法逻辑Agent继续检查结构和绑定。综合判定Agent保留各专项理由，使“有风险”和“没有复用价值”不会被混成同一种拒绝原因。

## 8 讨论

### 8.1 为什么限定为C++

本文限定 C++，优先利用 Clang 的类型、符号、宏和模板信息，但不把完整编译环境作为所有候选的必要条件。Tree-sitter降级路径保证在编译数据库不完整时仍能抽取三层基础候选和近似L-CSDC。研究比较的是同一C++任务中的解析能力差异，不开展多语言实证。

### 8.2 高频、优质与通用性的关系

高频表示模式在特定数据中重复，优质表示模式具有清晰意图且不含明显缺陷，通用表示模式可以跨文件或跨仓库复现。三者相关但不等价。本文用频率发现候选，再由语义、语法逻辑和代码异味三个专项Agent分别评估意图、结构合法性和潜在风险，最后用独立测试区域评价通用性。代码异味审查不是为了把所有非主流写法一律删除，而是阻止有可解释风险的坏习惯被系统自动放大；同样，通过异味审查也不能替代习语语义与复用价值判断。

### 8.3 大语言模型的角色边界

大模型不负责仓库全量扫描、AST构建或最终合法性证明。阶段4让语义分析、语法逻辑和代码异味审查Agent分别输出可审计证据，综合判定Agent按显式门槛裁决，规划合成与代码组装Agent只处理已经通过的模板。职责隔离的目标是减少一个模型在同一上下文中自我确认，而不是把多个Agent的共识当成事实；解析器与 `clang++ -fsyntax-only` 仍提供不可被LLM覆盖的确定性证据，低置信或冲突结论进入人工复核。

### 8.4 工程应用

习语库可以作为 IDE 推荐、代码审查、测试生成、规范识别和新成员培训的知识来源。实际部署还需维护习语版本、适用仓库、语言标准、最小依赖和废弃状态，防止旧习语随项目演化变成不推荐实践。

## 9 有效性威胁

### 9.1 内部有效性

- 聚类和LLM参数可能影响结果；应固定配置并重复实验；
- Tree-sitter按名称与作用域近似Def-Use，可能混淆遮蔽变量；必须与Clang符号绑定结果抽样比较；
- L-CSDC触发器和两跳预算可能漏掉较长习语或引入无关语句；由于不存在全仓习语真值，只报告分层抽样的 $EVY_{sample}$、最终输出中的VNG和预算敏感性，不宣称全仓召回；
- Clang编译数据库覆盖不完整可能使部分文件降级；应逐文件记录实际后端与能力掩码；
- 代码异味常依赖项目约定和上下文，LLM审查 Agent 可能产生漏报或误报；应固定异味分类与提示，保留上下文，并用多专家标注集评价；
- 多个Agent若使用相同基础模型，错误可能相关；应使用职责隔离的prompt、隐藏其他专项结论，并以Single-Agent和角色消融检验编排是否真正有效；
- 综合判定Agent可能越权重写专项结论，合成Agent也可能在反复修复中引入新逻辑；应采用机器可检验的裁决规则、限制合成输入和回流次数，并保存完整轨迹；
- 模板编译壳可能遗漏真实构建上下文；应同时在原仓库配置中验证；
- 随机按片段划分可能让近重复克隆跨越训练与测试集，从而虚高ISP和IC；应在划分前按文件、模块和克隆族分组；
- 模板匹配阈值、AST节点过滤和重叠匹配处理会影响IC/ISP；应在开发集固定并公开计算脚本；
- Haggis-CPP需要把Java/JDT实现迁移到Clang AST，C++节点映射、函数级AST森林和类型元变量可能改变原算法行为；应发布适配差异、与原实现的小型Java sanity check及采样收敛诊断，不声称完全复现原结果；
- LLM-Direct受文本分块、归并prompt和token预算影响；应同时报告预算匹配版本，固定分块顺序并重复运行，Full版本只能作为成本敏感性分析；
- Top-$K$可能偏向各方法原生排序较好的结果；应在测试前固定K，另报告完整输出的自动指标和多个K值的敏感性，不能只选择最有利的K；
- 人工标注可能带有个人风格偏好；应提供统一指南、隐藏方法与Agent结论、报告标注时长和一致性，并保留第三人裁决记录。

### 9.2 外部有效性

- 选取的仓库不能代表全部C++项目；应覆盖不同规模、领域和语言标准；
- 企业项目的宏、框架和编码规范可能与开源仓库不同；结论不应无条件外推。

### 9.3 构念有效性

- IC衡量AST节点覆盖，ISP衡量训练习语在测试区域的复现；二者及其F1不能单独证明习语“好”，也不能替代全仓召回或人工正确率；
- HVIP@K只评价被选入统一盲评池的输出正确性，不覆盖仓库中未被发现的习语或Top-$K$之外的长尾；VIY@K用于约束输出过少问题，但也不能代替完整输出上的Raw覆盖与复现；
- BCR只能证明候选规模得到保留，$EVY_{sample}$只说明抽样增强边界质量，VNG只说明轨道B对最终人工确认结果的可观测增量；三者均不能证明潜在习语已被完整发现；
- ALR@K依赖人工异味分类和严重度阈值；应报告类别级结果、误过滤率和标注一致性，不能把风格分歧都当作反模式；
- AvgAST、NSR和ANI只能作为结构规模或下游代码增幅统计，不能直接代表语义完整、功能正确、测试质量或规范识别准确率。

### 9.4 结论有效性

- 正式结果需报告样本数、方差、置信区间和适当的显著性检验；
- 多次比较应控制偶然显著性；
- mock数据仅用于规划，不能进入最终统计推断。

## 10 结论与未来工作

本文研究一种兼顾创新性、候选产量和实现成本的 C++代码习语挖掘方法，并将其固定为四阶段流水线：阶段1以双轨抽取保留语句、区域和函数三类基础候选，并用选择性L-CSDC补充有限的非连续静态依赖候选；阶段2执行结构—语义嵌入与密度聚类；阶段3进行簇后对齐、AST反统一和差异元素抽象；阶段4由语义、语法逻辑和代码异味专项Agent完成独立评审，经综合裁决、规划合成、代码组装、回流复审和静态验证形成知识库。Clang提供主实验精度，Tree-sitter提供可部署的降级路径。端到端实验以Haggis-CPP、LLM-Direct-Budget和可选Full版本为主要baseline，并用LineOnly、Fixed3Level、SemanticOnly、TokenAbstract、SingleAgent、NoSmell和NoSynthesis回答模块贡献。评价不构造全仓习语Ground Truth：完整输出使用Raw-IC、Raw-ISP、Raw-F1、AvgAST、OY、IV和Cost自动评价，统一Top-$K$盲评池只提供HVIP@K与ALR@K两个直接人工指标，并派生V-IC@K、V-ISP@K、V-F1@K和VIY@K。该设计在可接受标注成本下同时衡量覆盖、复现、结构规模、有效性、产量、静态可用性、成本和反模式风险。

后续工作首先是以真实代码和日志替换全部 [MOCK] 数据，完成专家标注和消融实验；其次研究习语随仓库版本演化的增量更新；最后探索习语在IDE推荐和自动代码审查中的应用。上述扩展仍限定于 C++，除非研究范围被用户重新明确修改。
