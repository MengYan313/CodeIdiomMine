# C++ 实验数据集分类与选取方法

## 结论

当前正式数据集固定为 23 个仓库。为支持后续分层实验，本研究采用两条彼此独立的
分类轴：

- **主领域**按项目的核心生产用途划分为 5 类，每个仓库只指定
  一个主领域；跨领域能力继续由 `project_type` 和 `idiom_focus` 多标签记录。
- **相对分析复杂度**按有效代码行数、核心源码文件数和阶段1候选数计算，分为
  低 8 个、中 8 个、高 7 个仓库。

主领域用于研究不同软件用途下的效果差异；相对分析复杂度用于研究流水线处理负荷、
成本和规模敏感性。二者都只用于结果分层，不参与项目去留、DBSCAN 参数、LLM
提示词、判断阈值或合成策略选择。

## 分类合同

### 主领域

主领域采用互斥标签，是为了让仓库宏平均能够按清晰分组复算，而不是断言项目只属于
一个领域。对于 `qbittorrent`、`mosh`、`CLI11` 等具有交叉属性的项目，以核心
交付用途确定主领域，其他属性保留在原有多标签中。

| 主领域 | 判定边界 | 仓库 | 数量 |
|---|---|---|---:|
| 数据表示与泛型基础库 | 主要提供格式、序列化、数据解析、反射或泛型值表示能力 | `cereal`、`fmt`、`json`、`magic_enum`、`tomlplusplus`、`yaml-cpp` | 6 |
| 开发工具与工程基础设施 | 主要服务构建、测试、日志或命令行接口等开发工作流 | `catch2`、`cli11`、`ninja`、`spdlog` | 4 |
| 网络与分布式系统 | 主要实现网络协议、通信、中间件、代理或异步服务 | `drogon`、`envoy`、`libzmq`、`mosh`、`uwebsockets` | 5 |
| 应用与跨平台界面 | 主要交付终端/桌面应用、界面运行时或布局能力 | `btop`、`polybar`、`qbittorrent`、`react-native`、`yoga` | 5 |
| 存储与并发基础设施 | 主要提供存储引擎、无锁容器或任务调度能力 | `concurrentqueue`、`leveldb`、`taskflow` | 3 |

### 相对分析复杂度

该字段衡量的是 CodeIdiomMine 对当前仓库的**相对处理负荷**，不是圈复杂度、
可维护性、缺陷密度或项目质量。只使用阶段1已经固定、且在阶段2与 LLM 之前可得
的三项指标：

1. `effective_line_count`：统一过滤后的有效代码行数；
2. `selected_file_count`：进入零构建解析的核心源码文件数；
3. `candidate_count`：函数、区域、语义切片和语句候选总数。

对正式仓库集合中的每个指标分别计算升序平均秩百分位 \(P_m(r)\)，并等权计算：

\[
C(r)=\frac{
P_{\mathrm{line}}(r)+P_{\mathrm{file}}(r)+P_{\mathrm{candidate}}(r)
}{3}
\]

随后按 \(C(r)\) 升序分成近似等频三层；当前 23 仓对应低 8、中 8、高 7。
指标相同使用平均秩，综合分相同使用 `slug` 保证边界确定性。该相对层级只对当前
冻结集合成立；如果正式仓库集合改变，必须重新生成清单并报告新的分层。

## 数据集选取方法

本数据集采用**有明确约束的目的性最大差异抽样**，目标是覆盖真实 C++ 工程中的
不同用途、规模和习语来源，而不是声称对全部 GitHub C++ 仓库进行随机抽样。选择
过程固定为以下漏斗：

| 阶段 | 判定依据 | 结果 |
|---|---|---:|
| 候选搜索 | 公开 GitHub 仓库、真实生产项目、C++ 主体、许可可核验、非归档且保持活动；star 与 fork 仅作背景，不设人气硬阈值 | 检查 27 个候选，其中新增 24 个、种子 3 个 |
| 源码入口审查 | 统一标准扩展名、核心源码范围和排除规则；不为单仓加入 Parser 特例 | 23 仓进入当前阶段1 |
| 零构建解析审计 | 每个扫描文件都有记录，路径安全且可复算；低 AST 覆盖率或头文件集中项目可“条件保留”，不以 Parser 易处理性代替项目质量 | 26 仓完成阶段1 |
| 阶段2适用性筛选 | 使用冻结的逐仓 DBSCAN 结果与具体簇语义，检查聚合副本主导、纯重复率、跨文件支持和强结构代理；不重新运行或按仓库改参数 | 排除 `cpp-httplib`、`entt`、`simdjson` |
| 正式冻结 | 保持逐仓发现隔离，后续不再根据真实 LLM 或最终 IC、ISP、F1 调整项目集合 | 正式数据集 23 仓 |

选择合理性来自五类互补证据：

1. **工程真实性。** 23 个项目均为公开、未归档且在元数据快照日前 365 天内有
   上游 push 的生产项目，不使用教学片段或纯测试语料替代真实工程。
2. **用途与语言特征覆盖。** 5 个主领域均有至少 3 个项目，同时覆盖 C++11、
   C++14、C++17、C++20，以及模板、RAII、并发、网络、解析、回调和平台抽象等
   多种习语重点。
3. **规模与处理负荷覆盖。** 数据集包含 2,911～428,842 行有效代码、7～3,780
   个核心文件，并通过相对分析复杂度保留低、中、高三层，而不是只选择大型明星项目。
4. **可复现与合法使用。** 每仓记录源码范围、远程地址、许可 SPDX、解析命令和
   产物路径；公开可访问仍不替代各许可证的署名与再分发义务。
5. **下游证据质量。** 阶段2筛选同时使用可复算指标与代表簇语义审查，排除了
   聚合发行副本或单文件局限主导的仓库，但没有把低 AST 覆盖率本身当作淘汰理由。

该方法仍有边界：项目不是概率样本；5 个主领域是当前研究的操作性目录；Envoy 与
React Native 是固定稀疏范围；条件保留项目存在头文件集中或解析恢复风险。因此
论文应报告全量 23 仓逐仓结果、仓库宏平均和分类分层结果，不得只挑选表现较好的
类别，也不得把类别差异外推为所有 C++ 项目的总体差异。

## 后续分层实验

后续实验可以在不改变正式主流程的前提下增加以下分析：

1. **主领域分层。** 对五类分别计算仓库宏平均、置信区间、输出产量和人工有效率；
   主结果仍保留全体 23 仓宏平均。类别内只有 3～6 仓时，以描述性差异和效应量
   为主，不单凭显著性下结论。
2. **相对分析复杂度分层。** 比较低、中、高层的 Raw-F1、V-F1、运行时间、
   峰值内存、LLM token/10KLOC 和失败率，检验规模增长是否只增加成本，还是同时
   改变候选质量。
3. **分层人工审计。** 在既有候选粒度和阶段分层之外，按主领域与复杂度层分配
   最小人工样本；自动指标仍覆盖全部输出，不能用分层抽样替代完整自动评价。
4. **二维探索。** 领域×复杂度交叉单元只作案例和趋势分析；当前空单元与小样本
   不支持完整双因素因果解释。
5. **稳健性补充。** 可按“保留/条件保留”、AST 覆盖率或头文件集中程度做补充
   敏感性分析，但这些标签不得回流为仓库专用参数或算法路由。

所有分层实验都必须继续逐仓独立运行相同 Parser、Embedding、DBSCAN、判断和
合成配置；分类只在逐仓指标完成后用于汇总。若未来扩充或替换仓库，应先冻结新的
选择清单、重新生成复杂度层级，再执行方法比较，不能依据最终效果补仓。

## 结构化证据

- `cpp-dataset-selection.json` 保存分类政策和正式仓库的人工主领域。
- `cpp-dataset-manifest.json` 在每个正式项目的 `classification` 中保存主领域、
  复杂度层、综合分、三项原始指标及各自百分位。
- `cpp-dataset-statistics.json` 保存领域分布、复杂度分布和交叉表。
- `scripts/analyze_cpp_dataset.py` 负责复算复杂度与校验逐仓分类、汇总和正式范围
  一致性。
- 阶段2排除的量化和语义依据见
  [C++ 聚类质量筛选报告](cpp-clustering-quality-screening.md)。
