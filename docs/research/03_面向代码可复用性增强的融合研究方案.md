## 摘要

代码复用是降低软件开发成本、提高代码质量和延长软件资产生命周期的重要手段，但现实工程中的可复用资源往往以两种相反形式被浪费。本文以“增强代码可复用性”为核心研究两条互补路径。C++代码知识侧采用固定的四阶段流水线：阶段1完成数据采集清洗、AST构建与进阶处理、双轨片段抽取和元数据组装，其中完整保留语句、区域和函数三类基础候选，并用选择性轻量语义依赖链（L-CSDC）补充非连续候选；阶段2完成Embedding嵌入、Cluster聚类与冻结结果上的仓库内保守归并；阶段3“多重可信门控”由 `idiom_judgment` 对单个簇执行完整成员规则过滤，规则只筛出高频、结构稳定且低语义的可抽象位置，再由语义/抽象Agent基于代表代码、词法去重变体、四项统计、规则初判和全部提案输出习语有效性及理由、决定抽象或保持原样，并把有效结果分为目录化通用习语或仓库专属习语，同时形成语义/复用价值业务评分，再由共享代码异味Agent输出独立审查理由并执行不可被业务分抵消的门禁；阶段4“关联闭环融合”由 `idiom_synthesis` 正式消费阶段3接受产物，自动加载代表区域上下文，再对同一区域内多个候选习语执行关系规划、代码组装和质量/有效性/类型复审，并使用同一异味合同对合成结果重新独立审查，只保留业务质量与异味门禁均通过的组合。最终知识库提供通用、专属和全量联合三种分析视图。阶段2簇到阶段4只保留不启动 Agent 的适配和严格阈值合同测试，不进入实际实验执行。解析层由 Tree-sitter/C++ Adapter 提供免目标项目编译、免链接、免执行的全量基础路径，并在安全可得时叠加 Clang 语义信息；全流程不要求目标仓库成功构建或运行，也不依赖运行时插桩、复杂LLVM IR映射或全程序别名分析。其端到端实验固定比较Haggis-CPP、预算匹配的LLM-Direct-Budget、Rules-Embedding-Clustering、IdioMine-CPP与完整CIMAS-CPP；LLM-Direct-Budget与Rules-Embedding-Clustering同时构成“仅LLM”和“仅规则分析+嵌入聚类”的端点消融，IdioMine-CPP作为前身方法“核心挖掘、独立判断、同区域直接合成”的C++简化迁移。完整输出采用统一自动指标评价，人工补充只允许使用预先冻结的公共样本，并对异味过滤执行分层事后审计。前端侧面向 WPF 遗留系统并固定以 MUI 为目标组件库，采用“依赖抽取—单组件迁移原语—完整迁移流程编排”三阶段Pipeline。阶段1由页面布局解析器、数据类解析器和资源依赖解析器组成：逐页面组件依赖树按 XAML 组件实例的布局包含层级构造；页面、数据、资源、样式和模板关系由规则优先拆为可稳定迁移的主结构与统一额外依赖边，动态键、反射、模板选择器等规则无法确定的关系才由 LLM 辅助分类。阶段2以组件为最小迁移单元：标准 WPF 组件通过规则映射定位 MUI 组件，自定义组件先由 LLM 总结其在代码段中的作用，再通过向量相似度检索 MUI 候选，最后把 WPF 代码与检索知识输入 LLM 生成 React 组件；该阶段专门说明 RAG 和单组件迁移能力，不定义组件树顺序，也不把子节点代码作为原语的固定输入。阶段3统一采用“规则解析—先拆迁移—后合引用—工具验证”：先迁移资源、数据类、样式/模板主体和主要页面结构，再按依赖类型恢复类型引用、资源键、样式继承、模板引用和额外页面导航；无法证明合法或等价的循环显式阻塞。组件仍按层级深度自底向上调用阶段2原语，并将直接子节点的已验证代码输入父节点。第二、三阶段共同构成多Agent方法核心，并通过编译、资源/样式/模板检查、渲染、视觉和交互验证形成工具反馈闭环；其中阶段2回答“单个组件如何迁移”，阶段3回答“该能力如何按统一拆合策略组装为完整工程流程”。

两项研究不共享同一数据集，也不假设 C++习语直接驱动 WPF→React 迁移；二者的统一性体现在共同解决“已有代码价值如何被重新利用”的问题，并采用“确定性结构分析缩小搜索空间、知识建模提供复用载体、LLM完成语义判断或重构、编译与测试工具保证结果可验证”的混合技术范式。本文进一步建立覆盖知识发现、仓库内部复现、功能保留、目标组件复用和验证可靠性的评价体系。通过两个独立实证研究及跨研究消融分析，论文将回答结构分析、知识增强、大模型推理和工具反馈如何协同提升软件复用能力。该研究有望为流行项目中的编程知识沉淀和遗留系统现代化提供统一的可复用性视角与可落地的方法框架。

## 1 研究背景

### 1.1 软件复用的两类资源困境

软件复用的经典定义强调由既有软件制品构造新系统，并把抽象、选择、专门化与集成视为复用技术的关键环节[E012]。在此基础上，从软件演化角度看，至少存在两类尚未被充分利用的资源。

第一类是**隐性知识资源**。成熟和流行项目经过长期迭代，形成了大量稳定的错误处理、资源管理、防御式检查、接口调用和控制流模式；代码自然性研究也表明大型软件语料具有可学习的统计规律[E063]。这些模式散落在源代码中，只有熟悉项目的开发者能够识别和复用。但“成熟项目中高频出现”并不保证实现优质，反模式、缺陷代码和历史坏习惯也可能因复制与团队惯性反复出现[E040][E036]。若只自动发现和抽象而缺少质量过滤，系统可能把坏习惯固化为可推荐知识。因此，知识显式化既要发现重复结构，也要在复用前识别并阻断不应传播的代码异味。

C++ 受控习语目录使用 thesis 统一编号：同行评审的预定义习语研究[E003]、
Coplien 专著[E111]与社区目录 *More C++ Idioms*[E025]提供分类语境，C++ Core
Guidelines[E112]、cppreference 的 RAII 和 Rule of Three/Five/Zero
[E113][E114]以及 Boost.Scope Scope Guards[E115]约束资源管理、特殊成员函数与
作用域清理的识别边界。在线指南和文档只作为类别与审计来源，不证明目标仓库中的
频率或方法效果；完整著录仍由同级 thesis 文献库统一维护。

第二类是**被技术栈锁定的软件资产**。传统桌面系统中已经实现的页面结构、数据展示、交互流程和领域功能具有继续复用的价值，但 WPF、XAML、MVVM 和企业控件依赖使其难以直接进入现代 Web 技术栈。遗留界面逆向工程与多目标UI研究早已表明，迁移需要恢复比表面控件标签更丰富的结构和设计信息[E013][E034][E014]；完全重写会丢失既有行为并产生高昂验证成本，机械转译又难以处理框架语义差异。

因此，增强代码可复用性既包括“**把值得复用的知识找出来**”，也包括“**让已有软件功能换一种技术形态继续被使用**”。前者对应代码习语挖掘，后者对应遗留系统前端迁移。

### 1.2 大语言模型带来的机会与限制

大语言模型具备代码语义理解、自然语言解释和代码生成能力，可以判断候选片段是否具有清晰意图，也可以把源框架代码重构为目标框架实现。RAG及面向代码文档检索的研究进一步说明，显式外部知识可以为生成提供可追溯上下文[E023][E024]。然而，端到端依赖LLM仍面临以下问题：

- 大型仓库和数百页面超出单次上下文，必须先进行结构化切分和候选压缩；
- 企业组件API、项目约定和上下文依赖不一定存在于模型参数中；
- 模型可能生成不存在的API、不合法模板或行为不一致的代码；
- 非确定性输出难以直接满足科研复现和工程审计要求。

这说明LLM更适合承担高层语义任务，而非替代解析器、聚类器、编译器和测试工具。两个子课题都采用传统程序分析与大模型协同的混合路线。

### 1.3 研究意义

从研究角度看，本文把代码复用从“已有模块的直接调用”扩展为两个过程：

1. **知识显式化**：把成熟项目中的隐性编程实践提取为参数化、可验证的习语；
2. **资产再生化**：把遗留系统中的既有功能转化为现代技术栈中的可维护资产。

从工程角度看，前者可以支持代码推荐、代码审查、测试生成和规范识别，后者可以降低遗留系统现代化中的重复开发和功能回归风险。二者共同服务于“减少重复劳动、保留已有价值、促进跨项目或跨技术栈复用”的目标。

C++路径还强调**方法自身的可复用性**：若每接入一个仓库都必须重建其专用工具链、
依赖和运行环境，挖掘方法就难以真正复用。ZBP 把“源码可得即可解析”固定为阶段1
入口合同，使结构分析可以跨构建系统、平台、依赖状态和不完整代码迁移；高级语义
信息按能力增量叠加，不把采用成本转嫁为语料遗漏。

## 2 核心概念：代码可复用性增强

### 2.1 可复用性的四个维度

本文不把“重复出现”直接等同于“可复用”。一个代码资产是否真正可复用，至少取决于四个维度：

- **可发现性（Discoverability）**：有价值的模式或功能能否从大规模项目中被定位；
- **可复现性（Reproducibility）**：是否能脱离单个变量、文件或局部位置，在同一资产边界的其他位置继续适用；
- **可执行性（Executability）**：抽象或迁移后的结果能否解析、编译、运行并保持必要行为；
- **可验证性（Verifiability）**：复用结果是否能通过结构、编译、测试和人工评价被审计。

可将总体可复用性理解为四个维度共同决定的能力：

\[
Reuse = f(Discoverability, Generalizability, Executability, Verifiability)
\]

该表达式是概念模型而非直接计算公式。C++代码习语研究重点提高可发现性和仓库内部复现性，同时用编译验证保证可执行性；前端迁移研究重点提高既有资产在新技术栈中的可执行性和可验证性，同时通过组件复用和迁移规则提高跨页面适用能力。

### 2.2 两条互补的增强路径

#### 路径A：从流行项目中生产可复用知识

```text
流行C++项目
  → 阶段1：数据/AST/双轨片段/元数据
  → 阶段2：Embedding嵌入与Cluster聚类
  → 阶段3：多重可信门控
  → 阶段4：关联闭环融合
  → 可供检索、推荐和下游任务使用的知识资产
```

该路径解决“优质代码已经存在，但没有被组织为可复用知识”的问题。

#### 路径B：从遗留系统中恢复可复用资产

```text
WPF遗留系统
  → 阶段1：布局/数据类/资源依赖三类Parser
       → 逐页面组件依赖树+各类主依赖结构+统一额外依赖边表+资源依赖映射表
  → 阶段2：标准规则/自定义语义检索 + MUI RAG + LLM的单组件迁移原语
  → 阶段3：主结构先拆迁移→组件层级树自底向上→页面整合→额外依赖边分类后合→统一验证
  → 编译、渲染、视觉和行为验证
  → 可继续维护和组合的现代前端资产
```

该路径解决“已有功能仍有价值，但被旧框架限制复用”的问题。

### 2.3 关联的边界

两个课题的融合是**研究目标与方法论上的融合**，不是强行构造直接数据流：

- C++习语库不直接作为 WPF→React 组件映射库；
- UI迁移结果也不作为 C++习语挖掘的训练数据；
- 两项实验分别使用适合自身任务的数据与指标；
- 跨研究结论聚焦共同假设：结构分析、知识建模、LLM语义能力和工具验证的组合，能否比单一规则或单一LLM更有效地提升复用。

这种设计既保持两个课题各自的科学完整性，也避免毕业论文变成两个无关项目的简单拼接。

## 3 两个科研项目的多层关联

### 3.1 研究目标关联

| 层面 | C++代码习语挖掘 | WPF→React前端迁移 | 统一含义 |
|---|---|---|---|
| 复用对象 | 编程模式与工程实践 | 页面、组件、交互与功能资产 | 复用已有代码价值 |
| 主要动作 | 发现、抽象、合成 | 解析、映射、重构 | 从具体实现得到可迁移形态 |
| 输出 | 参数化习语和知识库 | React组件与现代前端工程 | 可继续使用的代码资产 |
| 价值 | 避免重复解决相同编程问题 | 避免从零重写已有系统 | 降低重复开发成本 |

### 3.2 软件生命周期关联

流行项目代表经过充分演化的成熟代码，其问题是经验难以沉淀；遗留系统代表仍有业务价值但技术形态过时的代码，其问题是资产难以延续。前者关注**经验复用**，后者关注**功能复用**，共同覆盖软件生命周期中“知识积累—资产演化”的两个重要环节。

### 3.3 软件工程任务关联

两项工作都属于面向真实代码库的软件工程自动化任务，具有以下共同特征：

- 输入不是独立算法题，而是含依赖、约定和噪声的大规模工程代码；
- 输出必须与编译环境、API契约和项目上下文兼容；
- 评价不能只依赖文本相似度，需要结构、功能和人工质量指标；
- 结果需要保留来源、配置和中间产物以支持复现。

### 3.4 技术方法关联

| 共同方法阶段 | C++代码习语挖掘 | WPF→React前端迁移 |
|---|---|---|
| 结构解析 | 阶段1：Tree-sitter/C++ Adapter零构建基础、Clang可选增强、双轨片段和元数据 | UI阶段1：页面布局Parser解析XAML布局/组件，数据类Parser解析C#核心数据类，资源依赖Parser解析页面/组件/模板/数据/样式依赖 |
| 搜索空间压缩 | 阶段2：结构—语义Embedding、可选依赖摘要和DBSCAN聚类 | UI阶段2：标准组件规则映射，自定义组件功能总结与MUI向量检索；UI阶段3：依赖树驱动的顺序编排 |
| 知识表征 | 多重可信门控：单簇规则证据、完整本地成员、精简 LLM 簇视图、抽象提案/决策、高频低语义差异占位符和已验证候选习语 | 阶段2：MUI文本/代码/稀疏索引、组件元数据和完整API契约 |
| LLM作用 | 多重可信门控：基于代表代码、词法去重变体、四项统计和规则初判的语义/抽象决策、复用价值与共享异味审查；关联闭环融合：关系规划、组装、质量复审和共享异味审查；阶段3代表上下文只作本地门禁，阶段4上下文由编排层自动填充 | UI阶段2：自定义组件功能总结和知识增强组件生成；UI阶段3：子节点代码增强的父节点生成、页面整合与跳转逻辑联调 |
| 确定性约束 | AST绑定、局部依赖、解析与Clang语法验证 | 组件接口、TypeScript、ESLint和测试 |
| 反馈闭环 | 多重可信门控与关联闭环融合各自执行业务质量门禁，并分别运行不可抵消的共享异味门禁；异味过滤另做分层审计 | 错误分类、定向检索、局部修复 |
| 可追溯产物 | 片段、模板、专项报告、裁决、合成轨迹和验证状态 | 源文件、检索证据、代码和验证日志 |

### 3.5 大语言模型关联

LLM在两项工作中都不是唯一核心，而是传统工具无法完全覆盖的“语义桥梁”：

- 在习语挖掘中，多重可信门控先由规则读取完整成员并筛出可抽象位置，再由语义/抽象Agent读取代表代码、词法去重变体、四项统计和规则初判，输出 `is_idiom`、理由、通用或仓库特有类型及 `abstract/keep`；拒绝抽象的合格习语保持原样。共享代码异味Agent从独立维度评审同一精简簇视图并输出理由。阶段3代表上下文只作本地验证门禁。关联闭环融合由编排层自动填充代表区域上下文，再由关系规划、代码组装和质量/有效性/类型复审Agent处理多个阶段3习语并复用同一异味Agent合同、但对融合结果重新审查和分类；两个阶段的业务评分均不含异味，异味达到阈值时由独立门禁直接拒绝；
- 在UI迁移中，多Agent系统在组件和页面两个粒度上连接“WPF源框架语义”与“React/MUI目标实现”，并受依赖树、MUI检索证据和已验证接口约束；
- 两项工作都要求LLM输出受结构化schema、知识上下文和工具结果约束；
- 两项工作都可通过低温度、固定配置、日志记录和人工抽样提高可复现性。

### 3.6 质量保障关联

“高频出现”或“可以生成”都不等于“可以复用”。习语模板可能是高频反模式、语义不完整或无法实例化，迁移页面可能编译成功但行为错误。两项工作都采用分层验证；其中代码异味关卡仅适用于 C++ 习语路径：

```text
单簇规则合格 ─┐
语义/复用合理 ─┼→ 多重可信门控 → 关联闭环融合 → 契约/解析通过
异味风险可接受┘
  → 任务级有效
```

差别在于最后一层：习语通过仓库内候选域覆盖、跨函数支持、文件参考折外推敏感性和同仓下游任务验证，UI迁移通过渲染、视觉、交互和人工语义评价验证。

代码异味在此只表示“需要进一步审查的质量风险”，不等同于已经证明的缺陷；Fowler 的官方说明同样强调异味是指向潜在深层问题的表层征兆，而非问题本身[E108]。既有同行评审研究揭示了异味的长期存留、检测主观性以及模型与专家工具互补等边界[E040][E036][E028][E027]；LLVM Clang-Tidy 检查清单[E109]和 SEI CERT C++ 在线技术标准[E110]则分别提供动态维护的工具规则与安全编码规范，不是论文效果证据。C++中的资源所有权、底层接口、模板技巧和兼容性代码高度依赖上下文，因此共享异味Agent只输出固定类别内的严重度、置信度和可定位证据，风险分由确定性代码计算；达到阈值或分析失败时独立拒绝，不允许质量分抵消。当前先采用 Agent 调用 LLM 的实现，后续以 CLEAN++、Clang-Tidy 等静态工具作为基线或补充，并以总体、分阶段和逐类别人工审计检验准确性，不能把模型、工具命中或标准条文写成质量真值。

## 4 研究问题

围绕“如何增强代码可复用性”，本文设置五个研究问题。

- **RQ1：可复用知识发现。** 如何在保留语句、区域和函数三类大规模基础候选的同时，以轻量静态依赖补充非连续C++习语？
- **RQ2：知识质量、可移植性与应用。** 在不构造全仓习语Ground Truth的条件下，完整CIMAS-CPP相较Haggis-CPP、LLM-Direct-Budget、Rules-Embedding-Clustering与IdioMine-CPP能否取得更好的覆盖—复现、结构规模与成本权衡？仅LLM与仅规则分析+嵌入聚类的端点消融分别损失什么？相较前身方法核心挖掘、独立判断与同区域直接合成的C++简化迁移，完整候选、多重可信门控和关联闭环融合带来什么增益？L-CSDC能否产生轨道A无法得到、且经人工确认的非连续习语增量，零构建基础路径与Clang可选增强之间存在多大质量、覆盖、采用成本和性能差异？相比RuleOnlyJudgment、NoSmell、NoContext、SingleSynthesizer与NoSynthesis，多重可信门控和关联闭环融合能否减少反模式泄漏与错误模板，并提高复现和应用价值？
- **RQ3：遗留资产迁移。** 如何将规则优先的依赖分析、MUI RAG单组件迁移原语，以及“主结构抽取—先拆迁移—额外边后合—工具验证”顺序编排为完整流程，把 WPF 界面转化为可维护的 React/TypeScript 资产？
- **RQ4：迁移可靠性。** 阶段2的标准规则/自定义语义检索能否减少 MUI API 幻觉？阶段3的资源/数据类前置迁移、组件树按深度自底向上、直接子节点代码注入，以及数据/资源/样式/模板/页面额外依赖边的分类恢复，能否减少接口猜测、编译错误和交互偏差？LLM辅助依赖分析相较纯规则能覆盖多少动态歧义关系，又引入多少误判与人工复核？
- **RQ5：共同方法假设。** 在两个不同软件工程任务中，“结构分析 + 知识增强 + LLM语义推理 + 确定性验证”的混合范式是否均优于规则单独处理或LLM端到端处理？

RQ1–RQ2由代码习语子研究回答，RQ3–RQ4由UI迁移子研究回答，RQ5通过两个子研究中对齐的消融实验和综合讨论回答。

## 5 总体研究框架

### 5.1 双路径架构

```text
                       代码可复用性增强（CRE）
                                  │
                ┌─────────────────┴─────────────────┐
                │                                   │
        路径A：可复用知识生产                路径B：遗留资产再生
        流行C++代码仓库                     WPF传统/遗留系统
                │                                   │
       阶段1 数据/AST/片段/元数据           阶段1 布局/数据类/资源依赖Parser
                │                                   │
       阶段2 Embedding嵌入与聚类            阶段2 MUI RAG+单组件迁移原语
                │                                   │
       阶段3 多重可信门控                   阶段3 资源/数据类/单页/多页顺序编排
                │                                   │
       阶段4 关联闭环融合                   阶段2–3共享多Agent与编译/渲染/交互验证
                │                                   │
        C++代码习语知识库                  React现代前端资产
                └─────────────────┬─────────────────┘
                                  │
            共同基础：结构感知、知识建模、LLM协同、工具验证、可追溯性
```

### 5.2 统一处理原则

1. **源码可得即可解析**：C++阶段1不以项目编译、链接或执行成功为前提，Clang信息只作可选增强；
2. **先结构、后语义**：先用解析器和依赖图确定边界，再调用语义模型；
3. **先压缩、后生成**：先聚类或分层，避免LLM直接处理全仓库；
4. **知识显式注入**：把习语实例、组件API和已迁移接口作为可追溯上下文；
5. **频率与质量分离**：高频只用于发现候选，C++候选必须接受确定性规则、语义/复用价值和独立代码异味审查，不能自动把常见坏习惯当作习语；
6. **生成结果必须验证**：LLM判断和代码输出均不能绕过确定性检查；
7. **失败结果同样保留**：记录异味拒绝、语义拒绝、失败页面和错误类型，支持后续改进。

## 6 子研究一：流行C++项目的代码习语挖掘

### 6.1 研究目标

从流行且维护活跃的 C++项目中发现重复出现、不含明显代码异味、具有明确编程意图且能抽象为参数化模板的代码习语，使项目内隐的优质经验转化为显式可复用知识，而不是自动复制项目中的反模式。

### 6.2 核心方法：四阶段Pipeline

1. **阶段1——数据与习语表示构建。** 读取当前 C++ 源码，不运行其配置、依赖安装、代码生成、编译、链接、测试或二进制；由 Tree-sitter/C++ Adapter 执行零构建 AST、诊断、节点规范化、作用域恢复和源码映射，已有可信构建信息与 Clang 只提供逐文件可选增强；轨道A始终提取语句级、区域级和函数级基础候选，轨道B只对明确的跨边界局部Def-Use、控制或显式API配对执行最多两跳的L-CSDC扩展；两轨去重后组装来源、位置、能力掩码、依赖摘要、宏/模板标签和清洗记录等元数据。
2. **阶段2——Embedding嵌入与Cluster聚类。** 对每个仓库的候选独立计算代码语义向量和AST结构向量，将轻量依赖摘要作为可选增强；使用当前工程基线DBSCAN执行密度聚类和噪声过滤，参数由目标函数改进、warm-start的标准贝叶斯优化确定。代理模型沿用高斯过程（GP），采集函数沿用期望改进（EI），二者不作改动；“改进”只指目标组合跨文件复现供给、Top100头部复现和密度平衡三个无监督指标，并在目标评价时检查覆盖率和最大簇占比。warm-start只用于初始化已有观测。系统输出带支持度、内聚度及仓库内跨文件信号的候选簇；不同仓库的候选和向量不得混合，参数选择不得使用人工标签或最终评价指标。
3. **阶段3——多重可信门控。** 每次只处理一个仓库内归并后的阶段2聚类簇，先用确定性合同和低价值规则读取完整成员，只拒绝支持度不足、仓库混合、合同无效或确定性平凡的簇；抽象规则再对簇内实例进行保守角色对齐，只为数量足够、高频变化、结构位置稳定且不承载业务语义的变量或低语义字面量提出候选，调用目标、字段API、类型、控制结构、返回语义和哨兵值默认保留。语义/抽象Agent接收代表代码、按 C++ 词法 token 去重的其他真实变体、原始成员数/变体数/文件数/源码位置数、规则证据、全部提案和经验证代表上下文，显式返回 `is_idiom`、判断理由以及 `abstract` 或 `keep`；只能批准规则提案，由确定性代码应用交集。上下文只用于核验代表片段，不替片段补充相邻操作；一个完整语句、仓库专属模式或同文件多位置重复均可成为候选习语。有效响应中的 `keep` 或无提案使原代码保持不变，不会单独拒绝习语；整份语义/抽象响应在JSON修复和有界重试后仍失败时保留原代码作为审计证据，但语义与复用分安全降为0并拒绝。该Agent同时形成语义/复用价值业务分，并把能够精确对应受控 C++ 目录的有效习语归为目录化通用习语，把无法可靠对应的有效习语归为仓库专属习语（运行时标签为 `仓库特有习语`）。动作数量、代码长度和目录类型不直接参与裁决；跨文件等支持证据以及语义/复用单项分只进入一次业务总分，不再叠加硬门禁。`is_idiom=true` 且业务总分达到60即可通过业务裁决。共享代码异味Agent独立输出固定分类 findings 和审查理由。两个并行分支相互隔离，任一技术失败只拒绝当前簇并记录尝试数、失败类型与回退动作，不中断后续簇。最终裁决先应用业务门禁，再应用不可抵消的确定性异味门禁，给出 `accepted` 或 `rejected`。已接受产物中可抽象者保存抽象模板，其余保存原代码，同时保存类型和完整理由链。
4. **阶段4——关联闭环融合。** 处理单元是由完整成员证据证明共同出现于同一仓库、源码路径和函数/区域范围的至少两个阶段3已接受习语；显示标签和embedding相似度不能扩大分组，相同候选集合跨区域只保留一个稳定代表，候选组合在全局只执行一次。编排层在任何LLM调用前自动读取经项目、路径和范围验证的同区域上下文，失败时零调用拒绝。关系规划Agent选择具有数据流、控制流或资源生命周期关系的子集并给出理由，代码组装Agent按计划组合并保存组装依据，质量复审与阶段3共享的异味Agent再并行检查意图保留、习语有效性、当前目录化通用或仓库专属类型、质量增益和风险；阶段4类型必须针对融合结果重新判断，不能直接继承来源阶段3类型。共享异味Agent沿用完全相同的Request/Result、JSON Schema、分类和阈值，并通过 `related_examples` 接收已验证上下文、来源习语及其阶段3理由，但针对当前融合代码重新执行。合成代码还必须能在已核验上下文中定位、不同于任一单个来源，并且质量复审不得保留未解决问题。每个Agent的每次逻辑尝试只允许一次JSON修复，技术失败后最多重试一次；规划或组装失败会跳过尚未开始的下游Agent，质量与异味并行复审相互隔离，未预料的组级异常只跳过当前组。阶段2簇只通过统一适配器和更严格阈值的离线合同测试，不启动阶段4 Agent。阶段4输出是最终库：`accepted` 包含阶段3基础习语与去重后新增合成，`synthesized` 单独列出新增合成，来源候选只作为证据而不计作合成实例。

上述四阶段是CIMAS-CPP后续实现、实验消融、框架图和论文写作的固定基准。阶段内部的解析器、嵌入模型、聚类器或Agent模型可以替换，但不应随意改变阶段边界与顺序。Tree-sitter/C++ Adapter 基础结果覆盖完整语料和端到端实验；Clang 在可信编译信息可得的分层子集上量化语义增强，不强制对不可构建文件补造环境，以控制采用成本并保持 ZBP。

各专项Agent的职责必须保持独立。代码异味只表示风险，不等同于缺陷；通过异味审查也不能替代语义意图判定。规则合同失败、`is_idiom=false` 和异味门禁不可由高分补偿；规则、语义与复用三个连续分值只计算一次业务总分，避免对同一弱证据重复过滤。当前方案需与RuleOnlyJudgment、NoSmell、NoContext、SingleSynthesizer、NoSynthesis和静态规则工具等变体比较，并报告质量收益、调用成本、反模式泄漏和误过滤。

### 6.3 可复用性产物

每个习语不仅包含代码模板，还包含：

- 代表实例和出现位置；
- 参数类型和绑定约束；
- 自然语言意图；
- 适用前置条件；
- 目录化通用习语类型或 `仓库特有习语` 标签、类型判定理由及分类置信度；
- 当前目录与项目作用域，用于形成目录化通用、仓库专属和全量联合三种知识视图；
- 频率、内聚度和仓库内跨文件复现信息；
- 代码异味完整审查输入、固定分类、严重度、置信度、证据、确定性风险分和独立门禁；
- 单簇规则、完整本地成员、精简语义请求、四项簇统计、抽象提案、`is_idiom`、`abstract/keep` 决策、实际批准集合、语义/复用价值业务评分、共享代码异味报告、各 Agent 理由和裁决信息；
- 自动上下文证据、关系与合成计划、代码组装轨迹、合成结果的 `is_idiom` 与重新分类、质量复审业务分、各 Agent 理由、独立异味审查与静态验证状态；
- 异味过滤的分层审计样本、人工标签、总体/分阶段混淆矩阵和逐类别P/R/F1。

这使习语能够被下游任务检索和使用，而不仅是一个聚类标签。目录化通用习语以
`catalog_id` 支持跨仓库知识聚合和复用；仓库专属习语以
项目和阶段内记录身份保持作用域；全量联合视图用于总体分析而不抹去二者边界。

### 6.4 独立评价

评价不要求人工穷举整个仓库中的全部习语。端到端主实验固定比较Haggis-CPP、预算匹配的LLM-Direct-Budget、Rules-Embedding-Clustering、IdioMine-CPP与完整CIMAS-CPP；其中Haggis-CPP是Haggis概率树替换语法算法的C++复现[E002]，不是原Java工具直接支持C++。LLM-Direct-Budget和Rules-Embedding-Clustering分别是“仅LLM”和“仅规则分析+嵌入聚类”的独立baseline及端点消融。IdioMine-CPP保留依赖链候选、预训练代码表示、仓库内DBSCAN、ChatGPT判断和合成：用 `candidate_origin=semantic_def_use` 近似DCC，对每簇独立判断，只把代表位置完全相同视为同一区域，对每个至少含两个通过项的组尝试一次合成，合成成功后直接作为习语。它省略Java DvCFG、精确控制依赖、原作者关联启发式、多Agent处理与合成后复审，因此必须解释为简化迁移而非完整复现[E006]。只有规则基线执行最终种类截断：先过滤小簇，再按预注册固定值或聚类内部无监督规则确定比例，最后施加每项目100类的硬上限；100不是固定输出数量，也不是评价指标。Haggis-CPP、LLM-Direct-Budget、IdioMine-CPP和CIMAS-CPP均输出各自全部有效结果，不设置公共Top100。所有方法对每个仓库的完整合格源码独立发现并输出统一模板与来源证据；训练/开发/测试划分不参与发现。公共适配器只执行字段映射、统一测量和规范化文本精确去重，不替基线补做本文方法中的分析步骤。最终评价用轮转五折让每个文件一次贡献主覆盖足迹；`IC_raw` 是接受实例的候选域覆盖，主IC为其统一平方根变换，ISP衡量独立跨函数支持；只用参考文件折模板的泛化指标与完整AST分母指标同步保留。当前工程的九项自动指标和聚合口径以 `docs/guides/evaluation-metrics.md` 为准。

完整去重输出首先接受全自动评价：原始候选域覆盖 `IC_raw` 经统一平方根变换得到主IC，ISP表示跨函数域支持，主F1表示二者平衡；`IC_raw`/`F1_raw`、参考文件折泛化、完整函数AST分母和逐折机会加权结果作为强制敏感性字段。该无参数单调变换对所有方法一致，用于展开低覆盖差异且不改变覆盖排序。AvgAST衡量模板结构规模，输出产量OY约束结果数量，模板静态有效性IV检查代表证据回填与重新解析，Cost报告时间、峰值内存和LLM token/API成本。人工评价只核验跨方法精确去重后的统一Top-$K$盲评池，最低限度标注“有效习语/无效/依赖上下文”和“是否含严重代码异味”，由此直接计算HVIP@K与ALR@K，并复用同一标签派生V-IC@K、V-ISP@K、V-F1@K和每万行有效习语产量VIY@K。若某方法输出不足$K$项，不得补齐；自动指标仍覆盖其全部输出。IC/ISP不是全仓习语Recall/人工Precision，ANI1/ANI2也只表示历史下游任务的AST节点增幅。额外边级或模块级真值成本较高的DEP/DER、SD-F1、SL-F1和SRR不进入端到端主表；代码异味Agent的CS-P/R/F1与误过滤率仅在小型审计集上报告。详细实验设计见 `01_C++代码习语挖掘研究稿.md`。

## 7 子研究二：遗留系统的前端UI迁移

### 7.1 研究目标

把 WPF遗留系统中仍有价值的页面、组件、资源和交互迁移到 React/TypeScript，在 MUI 契约下形成可维护、可组合、可继续演化的现代前端资产。

### 7.2 核心方法：三阶段Pipeline

1. **阶段1——依赖抽取。** 由三类 Parser 组成：页面布局解析器识别并解析 XAML，提取页面布局、组件层次和 Binding/资源引用点；数据类解析器识别并解析 C#，提取与UI直接相关的核心数据类及成员定义；资源依赖解析器综合前两类输出与 ResourceDictionary/code-behind，统一解析页面、组件、模板、数据和样式五类依赖。逐页面组件依赖树直接按 XAML 组件实例的布局包含关系和深度构造，父子边不混入其他引用。对页面、数据、资源、样式和模板关系，规则分析根据符号、资源键、作用域、声明顺序和显式引用选择可稳定调度的主结构，并把闭环边和非主关系写入统一额外依赖边表。动态键、反射、模板选择器或间接字符串引用只有在规则无法确定时才由 LLM 辅助分类，且必须保存证据、置信度和未解析状态。阶段1输出逐页面组件依赖树、各类主依赖结构、统一额外依赖边表和资源依赖映射表。
2. **阶段2——单组件迁移方法。** 将组件定义为UI迁移的最小生成单元。对 WPF 标准组件，使用可审计规则定位候选 MUI 标准组件；对 WPF 自定义组件，先由 LLM 总结其在当前代码段中的展示、数据与交互作用，再通过向量相似度检索 MUI 组件或组合。随后将当前 WPF 组件代码、规则结果/功能摘要和候选 MUI 完整契约输入 LLM，生成 React/TypeScript 组件。本阶段独立展开 MUI RAG 知识库、文本/代码/BM25检索、组件级聚合和完整契约回填，但不规定组件树顺序，也不把已迁移子节点代码视为该最小原语的固定输入。
3. **阶段3——完整迁移流程与顺序编排。** 统一采用“先拆后合”：先暂不恢复闭环边，独立迁移静态资源、样式/模板主体和 C# 核心数据类声明；数据类相互引用在类型声明就绪后用同一类型模块或 `import type` 恢复，资源键引用在目标资源存在后恢复，样式循环仅在规则可证明无冲突时提取共同基础样式/token，模板递归展开或覆盖语义不明时显式阻塞。随后逐页面按组件层级深度自底向上调用阶段2原语，注入所有直接子节点的已验证代码；组件树完成后，以根节点融合资源、数据和样式依赖生成完整单页面。仅当所有单页面完成后，先按主页面依赖树修改主要跳转逻辑，再遍历统一额外依赖边表补齐返回、交叉跳转、次父导航和其他可恢复引用。每次“后合”都必须重新接受 TypeScript、import、资源键、样式继承、模板展开、渲染或交互验证。

阶段2与阶段3分别回答“单个组件如何利用RAG迁移”和“组件迁移能力如何按简单依赖顺序组装为完整工程流程”。阶段2不是真实迁移的完全体；组件树按深度自底向上、直接子节点代码注入、资源/数据类前置迁移、页面整合，以及各类额外依赖边的“后合”均属于阶段3。页面、数据、资源、样式和模板共享“规则优先—主结构/额外边—先拆后合—工具验证”框架，但使用不同的恢复规则；无法证明合法或等价的循环不自动合并。两阶段共享 tsc、ESLint、遗留模式检查、资源/样式/模板检查、渲染、视觉和交互测试反馈闭环。

### 7.3 可复用性产物

迁移结果不仅是“能显示的页面”，还应包含：

- 可复用React组件及明确props接口；
- 统一主题token和资源映射；
- 可复用的Binding、布局和事件迁移规则；
- 组件API检索与使用证据；
- 页面级验证日志和待人工处理事项。

### 7.4 独立评价

端到端主评价必须对传统规则、纯LLM、不拆组件的消融和完整MigraUI使用同一评测器。全自动主指标收敛为：页面编译通过率P-CPR、页面渲染通过率P-RPR、项目构建通过率PBPR；在最终页面DOM/可访问树上验证源组件实例契约的组件实例复刻率CIRR；目标路由图相对源确认边的Nav-P/R/F1及逐边自动导航测试NTPR；成对截图覆盖率SPC及条件SSIM/CLIP，其中SSIM和CLIP分别依据结构相似性与视觉—语言表征原始工作实现[E045][E038]；以及墙钟时间、内存、LLM调用和token/API成本。CIRR不要求目标存在独立React组件文件，因此RuleTrans-MUI、LLM-Direct-Budget和NoComponentSplit均可计算。组件C-CPR/C-RPR/C-CAPR、RAG检索、资源/数据/额外边恢复和局部视觉指标只作为适用方法的机制诊断；MP-FPR、VLM-JS和人工HSS只在预注册的关键流程或分层页面子集上补充，不进入端到端主排名。所有分母来自与迁移方法隔离、在实验前冻结并抽样核验的evaluation manifest；测试断言与参考截图不得进入方法上下文。详细设计见 `02_前端UI迁移研究稿.md`。

## 8 统一实验设计

### 8.1 两个独立实证研究

两项工作分别实验，避免不相容指标被强行合并：

- **Study A：C++习语挖掘实验**，评价仓库隔离发现、抽象、仓库内复现，并分别分析目录化通用知识、仓库专属知识及其全量联合视图；
- **Study B：UI迁移实验**，评价遗留资产在新技术栈中的保留、组件复用和可验证性。

### 8.2 对齐的基线逻辑

虽然两个任务的指标不同，但对比方法可以按同一逻辑组织：

| 方法类别 | C++习语挖掘 | UI迁移 | 目的 |
|---|---|---|---|
| 传统/结构基线 | Haggis-CPP；Rules-Embedding-Clustering；IdioMine-CPP | RuleTrans-MUI：传统GUI元模型/语义转编译范式的WPF→MUI规则适配，不使用LLM/RAG | 验证概率语法、确定性规则/表示学习及前身方法简化迁移的能力边界 |
| 直接LLM基线 | LLM-Direct-Budget | LLM-Direct-Budget：原始文件机械分包、预算匹配、无IR/RAG/组件拆分/工具修复 | 验证绕过结构化Pipeline时的语义能力、幻觉和成本 |
| 模块消融/降级 | LineOnly、Fixed3Level、SemanticOnly、NoSelectiveAbstract、RuleOnlyJudgment、NoSmell、NoContext、SingleSynthesizer、NoSynthesis | NoRAG、NoComponentSplit（OneShotPage）、TopDownComponent、NoChildCode、NoDependencySchedule、NoRepair | 分离目标知识、组件粒度、自底向上顺序、子节点代码、依赖编排和工具反馈的收益来源 |
| 完整混合方法 | CIMAS-CPP四阶段Pipeline | 依赖抽取—单组件迁移原语—完整迁移流程编排三阶段Pipeline | 验证协同效应 |

Haggis-CPP是对DP-pTSG习语挖掘算法的C++复现[E002]，不是直接运行原Java/JDT工具；实现参考[Haggis论文原文](https://homepages.inf.ed.ac.uk/csutton/publications/idioms.pdf)和[官方实现 `codemining-treelm`](https://github.com/mast-group/codemining-treelm)。IdioMine-CPP参考[IdioMine论文](https://doi.org/10.1145/3597503.3639135)与[作者实现](https://github.com/Yanming-Yang/idioMine)，公开DCC-lite替代、Embedding模型差异、同区域分组、判断/合成prompt、调用成本和全部简化操作。UI侧同样不存在可直接执行的WPF→React/MUI同行评审传统工具，因此RuleTrans-MUI必须写成传统GUI元模型、映射表和确定性模板范式的适配复现，公开规则、未支持项及与GWT/移动UI/GUIMigrator等来源方法[E018][E007][E008][E009]的差异，不能冒称原工具直接支持本任务。UI的LLM-Direct-Budget只允许目录/文件名/上下文窗口机械分包、逐包生成及一次无IR工程合并；不得使用Layout/Data/Dependency IR、页面/组件树、MUI检索、多Agent、自底向上顺序或编译反馈修复。所有UI方法共享空白目标工程、二进制资源副本和只读评测器，公共适配器不得补写代码。生成式UI方法使用同一基础模型，Budget近似匹配总token并至少重复3次；额外高预算运行只用于成本敏感性。两类研究的全部基线均不得看到测试断言、参考输出或人工标签。

### 8.3 RQ5的跨研究消融

RQ5不比较两个任务谁的指标更高，而比较同一方法论趋势是否在两项任务中重复出现。

两个子研究分别在自身样本单位上报告置信区间和效应量；对预注册的多方法/多消融比较采用Holm方法控制族错误率[E022]，不把来自不同任务的$p$值合并成一个总体显著性结论。

### 8.5 建议增加的上位指标

为加强论文主线，可在不替代子任务指标的前提下增加以下统计：

- **Reusable Knowledge Yield（RKY）**：通过多维专项评审、综合判定与静态验证的习语数 / 进入筛选的候选簇数；
- **Human-Validated Idiom Precision（HVIP@K）**：系统原生排序Top-$K$输出中经人工确认属于代码习语的比例；
- **Validated Idiom Yield（VIY@K）**：Top-$K$池中每万行有效C++代码产生的人工确认习语数；
- **Anti-pattern Leakage Rate（ALR@K）**：Top-$K$输出中被人工确认仍含严重代码异味的比例；
- **Cross-Context Reuse Rate（CRR）**：在独立文件或仓库中至少复现一次的习语数 / 习语总数；
- **Target Component Reuse Rate（TCRR）**：使用目标组件库实现的可映射UI节点数 / 可映射UI节点总数；
- **Functional Asset Retention（FAR）**：迁移后通过的关键交互数 / 原系统定义的关键交互总数；
- **Manual Rework Reduction（MRR-Work）**：相对人工或基线流程减少的人工修改量。

这些指标应报告清晰分母，避免把不同层级样本混在一起。

## 9 预期创新点

### 9.1 以双路径重新定义代码复用增强

将复用问题统一为“成熟项目隐性知识的显式化”和“遗留系统既有资产的现代化再生”，使代码习语挖掘与前端迁移不再是两个孤立应用，而是分别解决知识供给与资产延续问题。

### 9.2 面向C++的结构—语义习语知识生产

将CIMAS-CPP固定为四阶段知识生产流水线。阶段1参考IdioMine由依赖关系发现非连续子习语的思路[E006]，提出产量约束的双轨多粒度静态抽取：轨道A保留全部三层基础候选，轨道B以局部Def-Use、控制和显式API配对生成有限L-CSDC；Tree-sitter/C++ Adapter 以 ZBP 覆盖全量源码，Clang 通过能力掩码提供可选增强，从而同时验证解析质量与方法采用成本。阶段2对每个仓库独立使用结构—语义Embedding与DBSCAN密度聚类发现自然簇，再执行不跨仓且不反向调参的保守簇归并；阶段3以多重可信门控对单簇执行完整成员确定性规则、可抽象位置初筛、基于代表代码/词法去重变体/四项统计的语义 `abstract/keep` 决策、语义/复用价值业务评分与共享异味独立门禁；阶段4以关联闭环融合消费阶段3接受产物，自动加载代表区域上下文，再在同一区域内执行关系规划、代码组装、质量复审，并以同一合同对融合结果重新执行异味独立门禁。阶段2到阶段4只保留非执行合同适配。创新不依赖扩大分析复杂度，而在于同时保留高产量抽取、零构建可部署性、静态依赖增量、多重可信门控、关联闭环融合和可审计的反模式过滤。

### 9.3 面向遗留UI的知识增强资产迁移

将 WPF→React/MUI 迁移固定为“依赖抽取—单组件迁移原语—完整迁移流程编排”三阶段Pipeline。阶段1通过页面布局、数据类和资源依赖三类 Parser 显式化工程上下文：组件实例按 XAML 布局包含关系形成逐页面组件树；页面、数据、资源、样式和模板关系由规则优先地拆为主结构与统一额外依赖边，动态歧义关系才交由LLM辅助分类。阶段2将组件作为最小迁移单元，以标准组件规则映射和自定义组件 LLM 功能总结/向量检索两条路径定位 MUI 候选，再用RAG与目标组件文档知识约束 LLM 生成 React 组件[E023][E024]。阶段3采用统一“先拆后合”流程：先迁移主结构和各节点本体，再按依赖类型恢复类型、资源、样式、模板和页面额外边，并对每次合并执行工具验证；组件仍按层级深度自底向上，为父节点注入直接子节点已验证代码。创新重点不是增加复杂图算法，而是把“可复用的单组件RAG能力”、“子节点代码逐层传递的工程顺序”和“主结构/额外边的统一拆合机制”组合为简单可执行的迁移流程。

### 9.4 跨任务一致的混合智能方法论

在两个不同任务中对齐“结构、知识、LLM、验证”四类模块并开展消融，研究混合方法是否具有跨任务稳定性。创新点不在于简单使用某个模型，而在于明确不同技术的职责边界和协同机制。

### 9.5 多维可复用性评价

建立从发现、仓库内复现到执行、验证的评价框架，避免将高频、编译通过或文本相似度单独当作复用成功。

## 12 风险与应对

| 风险 | 可能影响 | 应对方案 |
|---|---|---|
| 两项工作语言和任务差异较大 | 融合显得抽象 | 以“复用目标+共同方法假设”关联，不虚构直接数据流 |
| 可复用性概念过宽 | 贡献不聚焦 | 固定四维定义，并把每个指标映射到具体维度 |
| 高频反模式被误收为习语 | 自动学习并传播坏习惯 | 保持代码异味专项Agent独立；分别记录论文证据、工具规则与注明访问日期的技术标准，报告反模式泄漏率和误过滤率 |
| 多Agent过度复杂但收益有限 | 调用成本上升、实验难复现 | 与RuleOnlyJudgment、SingleSynthesizer和角色消融对照；固定预算与每组候选上限，低贡献角色允许合并 |
| LLM异味审查存在漏报或误报 | 坏习惯漏入或合法习语被删除 | 使用相同异味分类、prompt、模型和风险阈值；分析失败时拒绝，低置信 finding 按确定性公式降低有效风险，并以独立专家审计量化误过滤和漏报 |
| Haggis从Java适配到C++后偏离原算法 | 传统基线可比性下降 | 明确称为Haggis-CPP算法复现，公开JDT→Tree-sitter C++映射与全部差异，并用小型Java sanity check和采样收敛诊断核对实现 |
| IdioMine-CPP简化精确DCC、关联与ChatGPT链路 | 前身方法基线被误解为完整复现 | 始终使用完整名称，公开DCC-lite、UniXcoder/GraphCodeBERT差异、精确同区域分组、独立判断、直接合成与无合成后复审，只作简化迁移 |
| 纯LLM与完整方法的输入或预算不公平 | 端到端结论被上下文覆盖和调用成本混淆 | 以LLM-Direct-Budget作为主基线匹配总token预算，Full版本仅作成本敏感性分析；固定机械分块与两轮prompt |
| UI传统基线并非原工具直接支持WPF→React | 规则基线被误写为已有工具复现或被本文实现优势污染 | 明确命名RuleTrans-MUI适配基线，公开来源范式、全部WPF/MUI规则、未支持项和适配差异；禁止调用本文RAG、LLM或额外边恢复 |
| UI主指标依赖本文组件文件结构 | 不拆组件的baseline无法公平计分 | 端到端使用最终页面可观察的CIRR；C-CPR、DCRC等只作适用方法的内部诊断，不适用项不填0 |
| 评测清单由本文阶段1产出 | Parser错误可能同时影响生成与评分并偏向完整方法 | 在迁移前独立冻结evaluation manifest，以源规则、WPF运行时证据和分层人工核验构建；测试断言对全部方法隐藏 |
| 无法穷举全仓习语Ground Truth | 不能计算全仓习语召回率 | 全部输出计算Raw指标；人工只核验跨方法去重的统一Top-$K$池并报告HVIP@K、ALR@K及派生V-F1@K、VIY@K，明确不作全仓Recall声明 |
| 原生Top-$K$排序质量影响人工结果 | 低质量排序可能掩盖方法的完整输出特征 | 实验前固定$K$，同时报告全部输出的自动指标与多个$K$的敏感性分析，禁止用人工标签重排或补齐结果 |
| 代码习语实证不足 | 后端路径可信度下降 | 补齐人工标注、仓库内分区复现和编译验证，限定为C++ |
| Clang或构建数据库成为隐性输入门槛 | 不可构建仓库被系统性遗漏，削弱方法可复用性 | 全量执行Tree-sitter/C++ Adapter零构建路径；Clang仅作能力标记的增强子集，分别报告覆盖和失败 |
| UI只有编译率或单一截图分数 | 前端路径结论过强 | 采用三级门控：全量构建、组件契约和导航边测试，关键流程E2E，以及携带SPC的全局/局部截图评价；VLM Judge仅作人工校准后的辅助证据 |
| WPF截图环境难以稳定复现 | 视觉比较覆盖不足或受DPI/字体/数据混杂 | 固定Windows VM、DPI、窗口、主题、字体、区域和数据；目标侧固定Playwright环境；报告SPC与缺失原因，多状态截图只做分层抽样 |
| LLM输出波动 | 难以复现 | 记录模型、prompt、温度和运行日期，并多次重复 |
| 企业数据不能公开 | 外部有效性受限 | 匿名化统计、公开替代数据、发布框架和评测协议 |
| mock结果被误用 | 学术诚信风险 | 全文显式标记，真实实验后逐表替换并保留日志 |

## 15 相关工作与参考文献组织建议

正式开题报告和毕业论文的相关工作应围绕统一问题组织，而不是把两个项目的文献机械拼接。建议分为五组：

1. **软件复用与软件演化**：解释可复用资产、知识复用、组件复用和遗留系统现代化的理论基础；
2. **代码习语、克隆、频繁模式与代码异味**：包括Haggis、IdioMine、预定义习语重构、AST/依赖图挖掘、代码表征聚类，以及反模式/代码异味检测与高频缺陷传播风险；
3. **代码大模型与知识增强软件工程**：包括代码嵌入、LLM代码理解、RAG、工具增强Agent和生成可靠性；
4. **遗留系统与跨框架迁移**：包括规则式转译、模型驱动工程、神经代码翻译和LLM辅助迁移；
5. **UI迁移质量评价**：包括编译与API校验、视觉回归、交互测试、人工语义等价和维护成本。

初始材料中的 Allamanis与Sutton代码习语研究、IdioMine、Pythonic idiom重构、Code Llama和CIMAS早期论文可作为第二、三组文献起点。UI迁移方向尚需系统补充原始论文和权威资料。正式综述应明确每类方法的输入粒度、知识来源、是否支持工程依赖、验证方式和局限，并在结尾导出本文的研究空白：现有工作较少从统一的可复用性视角同时研究“隐性代码知识的显式化”和“遗留软件资产的现代化再生”。

## 16 结论

本文以“增强代码可复用性”为核心，将流行 C++项目的代码习语挖掘与 WPF遗留系统的前端迁移组织为两条互补研究路径。代码习语挖掘以四阶段Pipeline将数据与片段表示、聚类发现、多重可信门控和关联闭环融合组织为可复现闭环；阶段1通过 ZBP 使源码快照无需成功编译、链接或执行即可进入全量解析，避免方法复用受制于逐仓库构建环境；阶段2在冻结 DBSCAN 后执行仓库内保守簇归并，阶段3先以完整成员规则初筛可抽象位置，再由LLM基于代表代码、词法去重变体和四项统计决定抽象或原样保留，并以独立异味审查阻断高频反模式；阶段4只正式消费阶段3接受产物，把同一区域内相互关联的习语融合为更完整的知识对象，阶段2直达阶段4仅保留非执行合同验证。最终习语库把能够精确对应受控目录的结果组织为可跨仓库聚合和复用的目录化通用习语，把其余有效结果组织为保持项目作用域的仓库专属习语，并提供二者并集的全量联合视图。前端迁移以“依赖抽取—单组件迁移原语—完整迁移流程编排”三阶段Pipeline把被旧框架锁定的界面功能转化为可维护、可组合的React/MUI代码资产。阶段2定义利用RAG迁移单个组件的能力，阶段3通过规则优先的主结构/额外边分析、“先拆迁移—后合引用—工具验证”、组件层级树自底向上、直接子节点代码向父节点传递和根节点页面整合，把该能力组装为简单、可追踪的真实工程流程；LLM只补充规则无法判断的动态语义关系。二者分别回答“已有优质代码如何被更广泛复用”和“已有系统功能如何在新技术栈中继续复用”。

两个子课题在数据和任务上保持独立，在研究目标上共同服务软件复用，在技术方法上共享结构分析、知识建模、LLM语义能力和确定性验证，在实验上通过对齐消融验证共同方法假设。由此，毕业论文不再是两个项目的并列汇编，而形成一个清晰的中心命题：**面向不同形态的已有软件资产，如何通过结构感知与大模型协同，使其从“存在于代码中”转化为“能够被发现、迁移、执行和验证的可复用能力”。**
